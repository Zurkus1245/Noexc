# 01. Конвенции требований NoExcuse

Статус: draft · Дата: 2026-11-23 · Основа: `00-validation.md`, `CLAUDE.md`, `NoExcuse_MVP_Plan.md` v1.1

Документ фиксирует схему ID, шаблон требования, критерии готовности, процесс изменений, формат матрицы трассировки и правило тега `[O#]`. Термины — см. `02-glossary.md`. Нефункциональные требования — см. `03-nfr.md`.

---

## 1. Схема ID

ID обязательны во всей команде: в заголовках требований, коммитах, тестах, API-контрактах и матрице трассировки. Свободные формулировки вида «как в экране логина» не допускаются.

| Префикс | Что обозначает | Формат | Пример формата |
|---|---|---|---|
| `EPIC-<N>` | Этап плана | `EPIC-0`…`EPIC-7` | `EPIC-1` |
| `FR-<MOD>-NNN` | Функциональное требование | MOD из списка ниже | `FR-<MOD>-NNN` |
| `BR-<AREA>-NNN` | Бизнес-правило | AREA из списка ниже | `BR-<AREA>-NNN` |
| `NFR-<CAT>-NNN` | Нефункциональное требование | CAT из списка ниже | `NFR-<CAT>-NNN` |
| `SCR-S##` | Общий экран (вход, онбординг, ошибки, офлайн) | две цифры | `SCR-S##` |
| `SCR-T##` | Экран тренера | две цифры | `SCR-T##` |
| `SCR-C##` | Экран клиента | две цифры | `SCR-C##` |
| `SCR-A##` | Экран админа (веб) | две цифры | `SCR-A##` |
| `API-<operationId>` | Операция API `/v1` | `operationId` из `packages/contracts` (camelCase) | `API-<operationId>` |
| `TC-<ID требования>-NN` | Тест-кейс | ID требования + порядковый номер | `TC-FR-<MOD>-NNN-01` |
| `[O#]` | Тег зависимости от открытого решения владельца | `O1`…`O8` | `[O3]` |

### 1.1. Модули FR-<MOD>

| MOD | Область |
|---|---|
| `AUTH` | Вход, регистрация, роли, сессии, MFA |
| `LINK` | Инвайт, связь тренер–клиент, согласия, пауза, отвязка |
| `CLIENTS` | Список клиентов, статусы, карточка, импорт CSV |
| `PLAN` | Блоки, тренировки, упражнения, подходы, шаблоны, версии плана |
| `CAL` | Календарь, назначение, перенос |
| `WORK` | Выполнение тренировки, факт (WorkoutLog) |
| `NUT` | План питания, КБЖУ, дневник еды |
| `PROG` | Вес, замеры, прогресс |
| `NOTIF` | Push, напоминания, уведомления о пропусках |
| `ACCT` | Профиль, TZ, экспорт и удаление аккаунта |
| `ADM` | Админка: пользователи, связи, аудит, запросы субъекта, верификация |

### 1.2. Области BR-<AREA>

| AREA | Область |
|---|---|
| `LINK` | Правила связи (один активный тренер, статусы связи) |
| `CONSENT` | Согласия: типы, версии, отзыв, каскад |
| `INVITE` | Инвайт: срок, одноразовость, погашение, лимиты |
| `SYNC` | Обновление данных на клиенте, мгновенное закрытие доступа |
| `DATE` | Даты, TZ клиента, «день клиента», DST |
| `GATE` | Правила гейта и северной метрики беты |
| `NUT` | Правила питания (КБЖУ, ввод, версии) |
| `SAFETY` | Безопасность контента для клиента: предупреждения, тон уведомлений, дисклеймер |
| `DATA` | Хранение, экспорт, удаление, аудит данных |

Зарезервировано: `BR-GATE-001` — порог северной метрики беты (см. `00-validation.md`, C3). Значение определяется отдельным требованием.

### 1.3. Категории NFR-<CAT>

`A11Y`, `I18N`, `PERF`, `PLAT`, `LIMIT`, `REL`, `SEC`, `PRIV`. Полный список — в `03-nfr.md`.

### 1.4. Правила ID

1. Номер `NNN` — трёхзначный, начинается с `001`, растёт по порядку внутри префикса.
2. ID никогда не переиспользуются. Удалённое требование получает статус `deprecated` и остаётся в реестре; его номер не отдаётся другому требованию.
3. Изменение смысла требования без сохранения поведения — новый ID, старый `deprecated` со ссылкой на новый.
4. Пропуски в нумерации допустимы.
5. Код, тесты и API-операции ссылаются на ID дословно. Ссылка без ID не принимается в ревью.
6. Ошибки (`code` в RFC 9457) — отдельный реестр в `packages/contracts`; они не имеют префикса требований и не переиспользуются.

## 2. Шаблон одного требования

Одно требование описывает **одно поведение**. Если в описании есть «и», «а также» или несколько самостоятельно проверяемых исходов — требование делится на несколько.

```markdown
### FR-<MOD>-NNN. <Заголовок: глагол + объект, до 80 символов>

- **Актор:** тренер | клиент | админ (роль RBAC) | система (воркер)
- **Предусловия:** что должно быть истинно до начала (состояние данных, согласия, статус связи, версия приложения)
- **Описание:** одно поведение, одним-двумя предложениями, без реализации
- **MoSCoW:** Must | Should | Could | Won't (для MVP; «Later» в плане = Won't)
- **Этап/EPIC:** EPIC-<N>
- **Критерии (Given/When/Then):**
  - Позитивный: Given … When … Then …
  - Негативный: Given … When … Then … → код ошибки `<CODE>` (RFC 9457)
  - Граничный (если есть числовой лимит или TZ/DST): …
- **Коды ошибок:** `<CODE>` — `<HTTP-статус>`, `<CODE>` — `<HTTP-статус>`
- **Связанные:** BR-…, NFR-…, SCR-…, API-…, TC-… (TC создаются при переходе в `implemented`)
- **Владелец:** роль (Продукт / Mobile / API / Platform / Дизайн)
- **Ревьюер:** роль или человек, **не равный автору**
- **Статус:** draft | agreed | implemented | verified | deprecated
- **Открытые решения:** [O#] или «нет»
- **История:** дата — что изменено — кем — ссылка на PR
```

Обязательные правила шаблона:

- **Минимум один позитивный и один негативный критерий.** Негативный критерий описывает отказ (чужой ресурс, истёкший инвайт, превышение лимита, отсутствие согласия).
- **Коды ошибок** — RFC 9457 `problem+json` с полями `status`, `code`, `detail`, `requestId`, `errors[]`. Клиент ветвит логику только по `code`.
- **Чужой ресурс и негативные состояния инвайта** возвращают `404` с `code: NOT_FOUND` и одинаковым телом. Не различаем «не существует», «истёк», «использован», «отозван» (см. `NFR-SEC-003`).
- **Владелец ≠ ревьюер ≠ автор** по смыслу: автор не одобряет собственное требование.
- **Критерии — проверяемые.** Формулировки «быстро», «удобно», «понятно» запрещены без числа или наблюдаемого признака.

### 2.1. Пример заполнения (формат, не требование)

```markdown
### FR-<MOD>-NNN. Показать состояние «не отправлено» при отсутствии ответа сервера

- **Актор:** клиент
- **Предусловия:** подход отмечен, сеть недоступна
- **Описание:** до ответа сервера подход отображается как «не отправлено» с кнопкой повтора.
- **Критерии:**
  - Позитивный: Given подход отмечен и запрос завершился ошибкой сети; When открыт экран тренировки; Then подход показан как «не отправлено» и доступна кнопка «Повторить».
  - Негативный: Given сервер ответил `201`; When экран обновился; Then статус «сохранено» показан только после ответа; «сохранено» до ответа не показывается.
```

## 3. Что считается «готово»

### 3.1. Готовность требования по статусам

| Переход | Условия |
|---|---|
| `draft` → `agreed` | Заполнены все поля шаблона; есть ≥1 позитивный и ≥1 негативный критерий; связи BR/NFR/SCR/API указаны; ревью пройдено ревьюером ≠ автор; [O#] либо снят, либо явно помечен в статусе |
| `agreed` → `implemented` | Код смержен; для API изменение в `packages/contracts` попало в тот же PR, что api и mobile (`CLAUDE.md` §6); TC созданы и связаны; `SCR-*` соответствует макету |
| `implemented` → `verified` | Все TC по требованию автоматизированы и зелёные в CI; для UI — прохождение на эталонных устройствах (iOS 16+, Android 9+) и проверка NFR из раздела «Связанные»; нет открытых дефектов уровня High |
| любой → `deprecated` | Причина и ссылка на замену записаны в «Истории»; требование не удалено из реестра |

Требование с тегом `[O#]` не переводится в `implemented`, пока владелец не подтвердил решение. Часть, не зависящая от решения, может быть реализована отдельно.

### 3.2. Готовность функции (набора требований)

Функция считается готовой, когда одновременно выполнено:

1. Все `FR` функции в статусе `verified` или явно `deprecated`.
2. Для каждого `FR` с данными клиента есть TC на IDOR (чужой ресурс → 404) и на отсутствие согласия/связи.
3. Все связанные `NFR` проверены по способу из `03-nfr.md`, результаты приложены к PR.
4. Контракт (`packages/contracts`) изменён аддитивно в `/v1` или выделен `/v2` (`CLAUDE.md` §6).
5. Матрица трассировки обновлена (раздел 5).
6. Нет открытых `[O#]` для смысла функции.
7. Саморевью diff пройдено; нет TODO по задачам текущего этапа, нет дублирования логики (`packages/*` проверен первым).

## 4. Процесс изменения требования

1. **Инициатор** открывает PR, меняющий файл в `docs/requirements/`. В описании PR: ID, что меняется, почему, влияние на `FR`, `TC`, `API`.
2. **Классификация изменения:**
   - *Редакционное* (опечатка, уточнение формулировки без изменения поведения) — ревьюер, статус не меняется.
   - *Поведенческое* (меняется, что видит или может пользователь, или критерий) — владелец и ревьюер; статус возвращается в `draft`; TC обновляются.
   - *Нарушающее контракт* (меняет `/v1`) — новый ID или `/v2`; старый требуемый путь `deprecated`, его клиентская поддержка ≥2 релизов мобильного приложения (`CLAUDE.md` §6).
   - *Смена решения `[O#]`* — см. раздел 6.
3. **Одобрение:** владелец требования и ревьюер ≠ автор. Для `LIMIT`, `SEC`, `PRIV`, `DATA` и `BR-CONSENT-*` — дополнительно владелец продукта и (для юридических формулировок) юрист.
4. **Синхронизация:** в том же PR обновляются матрица трассировки, `packages/contracts` (если затронут API) и TC.
5. **История:** каждое изменение фиксируется строкой в разделе «История» требования. Удаление строк из истории запрещено.
6. Изменение требования в статусе `implemented` или `verified` без PR с обновлением TC запрещено.

Вне процесса: правки в обход PR (прямой коммит в `main`), изменение ID, переиспользование номера.

## 5. Матрица трассировки

Файл: `docs/requirements/traceability.md` (создаётся при первом заполнении FR; в рамках этих трёх файлов не создаётся).

| FR | BR / NFR | EPIC | SCR | API | TC | Статус |
|---|---|---|---|---|---|---|
| `FR-<MOD>-NNN` | `BR-<AREA>-NNN`, `NFR-<CAT>-NNN` | `EPIC-<N>` | `SCR-<X>##` | `API-<operationId>` | `TC-FR-<MOD>-NNN-01` | draft / agreed / implemented / verified / deprecated |

Правила:

- Одна строка — один `FR`. Несколько `BR`/`NFR`/`API`/`TC` перечисляются через запятую.
- Пустая ячейка `TC` или `API` при статусе `implemented` и выше — дефект ревью.
- Пустая ячейка `SCR` для клиентского/тренерского UI — дефект; для API-only требований ставится `—`.
- Матрица обновляется в том же PR, что и изменение требования.
- Обратная проверка (раз в спринт): каждый `EPIC` имеет ≥1 `FR` в статусе `agreed` или выше; каждый `Must` связан с `TC`.

## 6. Правило тега [O#]

`[O#]` ставится на требование или критерий, смысл которого зависит от открытого решения владельца.

Открытые решения (по `00-validation.md`, раздел 6). Все O1–O8 приняты в документах как рекомендованные оркестратором; подтверждение владельцем не получено.

| ID | Вопрос | Рекомендованный вариант |
|---|---|---|
| O1 | Один аккаунт = одна роль? | Да в MVP |
| O2 | У клиента может быть два тренера? | Нет: одна связь `active` или `paused` на клиента |
| O3 | Пауза закрывает доступ тренера к данным? | Нет: пауза отключает напоминания и пропуски; клиент запрашивает, тренер подтверждает |
| O4 | Админка к бете: веб или runbook + скрипты? | Admin-lite к бете, полная веб-админка к запуску |
| O5 | Что в Must беты? | Экран «кому нужна реакция», напоминания клиенту, импорт CSV — Must; комментарий к тренировке — Should |
| O6 | Питание в бете: КБЖУ или «ккал/день»? | КБЖУ по плану; дневник еды клиента — Should |
| O7 | Страна, язык, юрлицо | Не решено: язык один, строки в словаре |
| O8 | Тренеры онлайн или офлайн/гибрид? | Только онлайн-тренеры с 10+ клиентами |

Правила работы с тегом:

1. Формат: тег в конце заголовка требования и в строке «Открытые решения» — например, `[O3]`. В тексте критерия тег допустим, если критерий зависит от решения.
2. Требование с тегом в статусе `agreed` означает: принят рекомендованный вариант, и владелец об этом знает. Для `implemented` тег должен быть снят.
3. Снятие тега — одним PR, который обновляет все требования с этим тегом (поиск по `[O#]`), и отмечает решение в `00-validation.md` или в отдельной записи решения.
4. Если решение отличается от рекомендации, затронутые `FR` и `NFR` переходят в `draft`. Если поведение меняется, применяется правило раздела 1.4 (новый ID, старый `deprecated`).
5. Требования, зависящие от `[O#]`, не реализуются через флаги, захардкоженные под рекомендацию (`CLAUDE.md` §0). Вариант выбирается после решения.

## 7. Прочие правила

- Язык документов: русский. Идентификаторы, коды, имена полей API и таблиц — английские, как в `CLAUDE.md`.
- Значения, которые не утверждены, помечаются фразой «предложено, утвердить». Такие значения в `03-nfr.md` и в требованиях не считаются согласованными, пока не сняты.
- Экраны и состояния, которые в требованиях упомянуты, но не описаны, — дефект. Минимальный набор состояний на экран: загрузка, пусто, ошибка сети, офлайн, ошибка сервера, доступ запрещён (404 как «не найдено»).
- Тексты уведомлений на экране блокировки не содержат PII и данных здоровья (`NFR-PRIV-001`).
