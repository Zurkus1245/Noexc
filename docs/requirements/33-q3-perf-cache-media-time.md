## Часть 1. Анимации

**Принципы.**
1. Анимация объясняет изменение состояния (появление, переход, подтверждение). Декоративных анимаций в MVP нет.
2. «Сохранено» показывается только после 2xx (BR-SYNC-002); анимация успеха не стартует раньше ответа.
3. Анимация не скрывает ошибку: баннер ошибки и «Не отправлено» появляются без задержки и сами не исчезают.
4. Переходы не длиннее 350 мс. Циклических анимаций нет, кроме системного индикатора загрузки.
5. «Уменьшить движение» отключает движение; смена состояния остаётся статичной (NFR-A11Y-007).

**Бюджет 60 fps.** Цель: 60 fps на эталонном устройстве (EPIC-0), бюджет кадра 16.6 мс. Анимации по таймеру и жестам идут на UI-потоке (worklets). Предложено: не более двух одновременных анимаций на экране; списки от 50 элементов виртуализированы (NFR-PERF-005). Порог: не более 1% кадров дольше 33 мс в сценарии «таймер отдыха + список 300».

**Класс решения (ADR).**

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| `react-native-reanimated` (shared values, Layout Animations entering/exiting) | UI-поток, New Arch | новая зависимость, версия по Expo SDK | **выбрано** для таймера и подтверждения подхода |
| RN `Animated` + `useNativeDriver` | без зависимости | только opacity/transform, нет Layout Animations | допустимо для fade скелетона |
| Lottie | богатая графика | декор, рост сборки (NFR-PLAT-004) | отклонено в MVP |

**Токены `motion` в `packages/ui` (предложено).** Длительности: instant 100 мс, short 150 мс, medium 250 мс, long 350 мс (верхняя граница переходов). Кривые: standard `cubic-bezier(0.2, 0, 0, 1)`, enter `(0, 0, 0, 1)`, exit `(0.3, 0, 1, 1)`. Токен `reduced`: длительность 0, без transform. Литералы длительностей и кривых в экранах запрещены (CLAUDE §0), проверка lint-правилом.

**Режим «уменьшить движение».** Источник: `AccessibilityInfo.isReduceMotionEnabled()` и подписка `reduceMotionChanged`; хук `useReduceMotion()` в `packages/ui`. При включении: длительности 0, кольцо таймера заменяется цифрой, скелетон статичный, подтверждение — текст и haptic. Примечание: WCAG 2.2 критерий 2.3.3 относится к AAA, а не к AA; режим принят как продуктовое требование NFR-A11Y-007 (OQ-6). WCAG 2.2.2 (A/AA): кнопки «Пауза» и «Пропустить» таймера доступны всегда.

**Таймер отдыха и подход (FR-WORK-102, FR-WORK-103).**
- Отсчёт по часам: `endAt = Date.now() + restSec`. После возврата из фона остаток = `endAt − now`, без сброса.
- Кольцо-прогресс на UI-потоке; цифра обновляется раз в секунду.
- Конец отдыха: haptic `notificationSuccess`. Звук выключен по умолчанию, опция в настройках (предложено).
- Подход: «Отправка…» (нейтральный цвет) → «Сохранено» (после 2xx, haptic `impactLight`) → «Не отправлено» + «Повторить» (ошибка или таймаут 15 с).
- `expo-haptics` — новая зависимость, мала по размеру; обоснование в PR.

**Загрузка и запреты.** Скелетон — только при загрузке дольше 150 мс (предложено), повторяет форму контента, в reduce motion статичен. Запрещено: показывать данные анимированным появлением до ответа; fade-out ошибки; «успешную» анимацию до 2xx. Офлайн-баннер скрывается только после успешного запроса.

**Перечень анимаций MVP.**

| Анимация | MVP | Комментарий |
|---|---|---|
| Кольцо таймера отдыха | да | Reanimated, UI-поток |
| «Отправка» → «Сохранено» (150 мс) | да | только после 2xx |
| Скелетон → контент (250 мс) | да | только при загрузке > 150 мс |
| Появление баннера ошибки (fade 150 мс) | да | без задержки |
| Переходы экранов, bottom sheet, pull-to-refresh | да | системные, не кастомизировать |
| Переход «версия плана обновлена»; Layout animation списка календаря | нет | отложено, второе — до замера fps |
| Конфетти, «поздравляем», параллакс, Lottie, shared element | нет | декор, запрещено или не окупается |

**Тестирование.** Unit: `useReduceMotion` с моком `AccessibilityInfo`; таймер с подменой часов (остаток после фона 30 с). Maestro на эмуляторе с reduce motion: сценарий подхода без анимации, текст «Сохранено» есть. Производительность: `dumpsys gfxinfo` и Instruments Core Animation, сценарий «таймер + список 300». Риски: версия Reanimated против Expo SDK; поведение на Hermes.

## Часть 2. Кэширование

**Слои.** L1 память — TanStack Query с `staleTime`/`gcTime` по классам данных. L2 персистентный — нет в MVP (OQ-1). L3 HTTP — `ETag`/`If-None-Match`, `Cache-Control`. L4 диск изображений — `expo-image` (ADR). L5 CDN — EU CDN для HLS-сегментов. Хранилище: SecureStore для токенов, MMKV для настроек (см. ниже).

**Данные → слой → TTL → инвалидация.**

| Данные | Слой | staleTime / gcTime | Инвалидация |
|---|---|---|---|
| Токены сессии | SecureStore | срок сессии | выход, 401 после неудачного refresh |
| Профиль (`me`) | L1 | 5 мин / 10 мин | мутация профиля, focus |
| Статус связи | L1 | 0 / 5 мин | focus, push `link_changed`; 403/404 → удалить ключ |
| «Сегодня» | L1 | 30 с / 5 мин (BR-SYNC-001) | focus, pull, push `plan_changed`, мутация подхода |
| Календарь (диапазон) | L1 | 30 с / 5 мин | focus, pull, мутация переноса или отметки |
| План (версия N) | L1 + ETag | 5 мин / 10 мин | push `plan_changed`; сверка ETag при открытии |
| Прошедший день (снимок) | L1 | неизменяем / 5 мин | выход, отвязка |
| Вес, замеры, КБЖУ, итоги (ст. 9) | L1 только | 60 с / 2 мин | мутация, отзыв `health_data`, выход |
| Тренер: клиенты, «кому нужна реакция» | L1 | 60 с / 5 мин | focus, pull, push `client_event` (без ID и PII) |
| Подписанная ссылка видео | L1 | TTL ссылки − 60 с | истечение |
| Постер, превью; HLS-сегменты | L4 диск; L5 CDN | 30 дней; 7 дней | новая версия ассета (версия в ключе или пути) |
| Словари, версия приложения | HTTP ETag | 24 ч | ETag |
| Локальные настройки (единицы) | MMKV | бессрочно | выход (очистка ключей пользователя) |

Ключи TanStack: `['me']`, `['link']`, `['today', date, tz]`, `['calendar', from, to]`, `['plan', linkId, version]`. Только внутренние ID, без имён.

**HTTP-политика (предложено).** Health-эндпоинты (вес, замеры, КБЖУ, факт): `Cache-Control: no-store`, чтобы OS-кэш (NSURLCache, OkHttp) не сохранил данные ст. 9. План и календарь: `Cache-Control: private, no-cache` и слабый `ETag` от `planVersion` и `updatedAt`, 304 при неизменности. Мутации и прочие списки: `no-store`. CDN API не кэширует. Допущение: 40–60% запросов «Сегодня» получают 304 без тела.

**Хранение и запреты.**

| Класс | Решение | Обоснование |
|---|---|---|
| Токены | SecureStore | NFR-SEC-006 |
| Настройки без данных здоровья | MMKV (по умолчанию не шифрует) | CLAUDE §3; о здоровье в MMKV ничего нет |
| Кэш API | TanStack в памяти | в MVP нет офлайн-записей; ст. 9 не на диске |
| Офлайн-план (если OQ-1 = да) | SQLite с шифрованием, ключ в SecureStore, LRU, 3 версии на связь, 50 МБ | ст. 9 на диске только зашифрованно; ADR |
| Диск изображений | `expo-image`, LRU 200 МБ (предложено) | медиа без данных здоровья |

Запрещено кэшировать: токены вне SecureStore (TanStack, MMKV, логи, Sentry breadcrumbs); health-данные в логах, аналитике, Sentry, crash-отчётах, тексте push, персистентном кэше MVP и OS HTTP-кэше; открытые коды инвайтов; подписанные ссылки на медиа в персистентном хранилище; ПДн в ключах запросов.

**Очистка кэша.**

| Событие | Действия |
|---|---|
| Выход (FR-AUTH-003) | `queryClient.clear()`; удалить токены; очистить ключи пользователя в MMKV; очистить диск изображений. Локально, даже без сети |
| Отвязка клиентом или `end` (FR-LINK-119) | `removeQueries`: `['today']`, `['calendar']`, `['plan', linkId]`, `['link']` |
| Отзыв `health_data` (FR-LINK-114) | `removeQueries` по всем ключам ст. 9 |
| Отзыв `coach_access` (FR-LINK-113) | удалить все тренерские данные и ключи связи |
| Удаление аккаунта (FR-ACCT-003) | как выход, плюс все настройки и диск |
| 403/404 на связанный ресурс | удалить ключ ресурса (BR-LINK-007) |

Локальная очистка выполняется сразу; серверный отзыв — при подключении (FR-AUTH-003). **Вытеснение и размер (предложено):** L1 `gcTime` 2–10 мин, ключи только для смонтированных экранов; диск LRU 200 МБ; SQLite LRU по `lastAccess`, 50 МБ. Видео на устройстве не сохраняется.

## Часть 3. Медиа и нагрузка

**Пайплайн видео техники (предложено, EPIC-5).** Исходник загружает администратор контента (допущение: тренеры не загружают в MVP). API выдаёт presigned PUT: TTL 15 мин, один объект, фиксированный content-type, максимальный размер в политике. Объект хранится в S3-совместимом хранилище в ЕС с версионированием. Событие загрузки ставит `video.transcode` в pg-boss; worker делает ffprobe, HLS ABR (360p, 540p, 720p; сегменты 4 с), постер и превью, манифест по версии `…/{assetId}/v{n}/master.m3u8`. API выдаёт подписанный URL манифеста (TTL 15 мин), сегменты отдаёт CDN.
Лимиты (предложено): исходник до 200 МБ, до 60 с, до 1080p, mp4 или mov, H.264 или HEVC. Превышение — `VALIDATION_FAILED` до загрузки.
**Блокер:** права на контент не решены (FR-WORK-108 — Should). Ингест не запускается до решения (BL-PERF-08).

**Формула.**
- Трафик CDN в месяц, ГБ = N × V × T × B / 8 × 4.33 / 1000. N — клиенты; V — просмотры в неделю на клиента; T — секунд на просмотр; B — Мбит/с.
- Стоимость egress ≈ трафик × тариф EU CDN. Пиковая конкуренция ≈ (N × V / 7) × f × T / 3600 × k (f — доля пикового часа, k — коэффициент пика).
- Хранилище, ГБ ≈ N_роликов × T × Σ(B по ступеням) / 8 / 1000.

**Расчёт на примере.**

| Параметр | Значение | Метка |
|---|---|---|
| Тренеры / клиентов на тренера | 100 / 30 | задано (лимит 100, NFR-LIMIT-001) |
| N | 3 000 | 100 × 30 |
| Тренировок в неделю × упражнений | 3 × 6 | допущение |
| Доля упражнений с открытием видео | 20% | допущение |
| V = 3 × 6 × 0.2 | 3.6 просмотра в неделю | расчёт |
| T / B | 30 с / 1.5 Мбит/с | допущение (ролики 15–60 с; 540p–720p) |
| Объём просмотра / клиента в неделю | 5.6 МБ / 20 МБ | расчёт |
| **Трафик в месяц, базовый** | 3 000 × 20 × 4.33 ≈ **260 ГБ** | расчёт |
| Стоимость egress | 260 × €0.02–0.05 ≈ **€5–13 в месяц** | тариф — допущение |
| Максимум клиентов (100 × 100, V = 3.6) | ≈ **0.87 ТБ**, €17–43 | допущение |
| Все упражнения (V = 18) | ≈ **1.3 ТБ**, €26–65 | допущение |
| Пиковая конкуренция, базовый | 10 800 просмотров в неделю → 1 543 в сутки → 231 в пиковый час (f = 15%) → ≈ 2 потока; k = 3 → ≈ 6 | допущение (f, k) |
| Хранилище: 300 роликов, Σ = 4.8 Мбит/с | ≈ 5.4 ГБ; с версиями и постерами ≈ 11 ГБ | расчёт |

Вывод: стоимость определяется egress, а не хранением или числом потоков. Origin-нагрузка мала при доле попаданий в CDN не ниже 90% (допущение).

**Трафик API.**

| Запрос | Частота (допущение) | В сутки |
|---|---|---|
| GET «Сегодня» | 2 открытия + focus на клиента | ≈ 8 000 |
| GET календарь | 1 открытие и ≈ 5 переключений в неделю | ≈ 2 000 |
| POST подхода (idempotent) | 54 в неделю на клиента | ≈ 23 000 |
| Тренер: «кому нужна реакция»; URL видео | 3 в сутки на тренера; 3.6 в неделю на клиента | ≈ 1 800 |
| **Итого** | | **≈ 35 000 в сутки; среднее ≈ 0.4 rps; пик ×3 ≈ 1.2 rps** |

Запас до NFR-PERF-003 (50 rps) — не менее 40×. Polling отсутствует (CLAUDE §6): актуальность дают focus, pull и push-инвалидация с типом события без ID и PII. iOS может не доставить фоновый push, поэтому основной механизм — focus. Всплеск после публикации плана сглаживается случайной задержкой 0–30 с на клиенте (предложено).

**Нагрузка на БД (оценка).** `CalendarEntry` ≈ 470 тыс. строк в год. Подходы отдельными строками дали бы ≈ 8.4 млн в год; предложено: `WorkoutLog` — строка на тренировку с JSON-снимком подходов (≈ 0.47 млн в год). `PlanVersion` около 10 КБ на версию, менее 1 ГБ в год. Чтение «Сегодня» по индексам `CalendarEntry(clientId, date)` и `PlanVersion(linkId, version)` — ожидаемо менее 10 мс (допущение, проверить `EXPLAIN ANALYZE`). Без N+1 (CLAUDE §7).

**Пагинация и лимиты.** Курсор `{items, nextCursor}`, limit по умолчанию 20, максимум 100 (CLAUDE §6). Список клиентов тренера до 100 — 5 страниц, виртуализация в UI. Календарь: `from/to` не более 42 дней (FR-CAL-105). Импорт CSV: до 200 строк (NFR-LIMIT-011).

## Часть 4. Время и уведомления

**Правила.**
1. Все моменты времени — UTC, ISO-8601 с `Z` (CLAUDE §6).
2. Дата тренировки и пропуска — `DATE` в часовом поясе клиента (BR-DATE-001). «День клиента» — календарный день в его поясе, с 00:00 местного.
3. Пояс — IANA-строка в профиле, проверка `IanaTimezoneSchema`. По IP пояс не определяется (приватность; VPN даёт ложную локацию). Подсказка — настройки ОС, подтверждает пользователь.
4. Пропуск отмечается только после окончания дня клиента (BR-DATE-002, BR-DATE-005).
5. Напоминание хранится как локальное время клиента и IANA-пояс; UTC-момент `nextFireAt` вычисляется отдельно.
6. Смена пояса не сдвигает даты календаря и фактов, пересчитывает только `nextFireAt` (BR-DATE-003).

**Модель напоминания (предложено).** Поля: `reminderId`, `linkId`, `localTime` (HH:mm), `leadMinutes` (0, 30, 60, 120), `timezone`, `nextFireAt` (UTC, индекс), `enabled`, `lastSentLocalDate`.
- `nextFireAt`: локальная дата D — сегодня клиента, если `localTime − lead` ещё не прошло, иначе завтра. UTC находится подбором момента, у которого местные части совпадают с целевыми (Intl). После отправки пересчёт на следующий день. Напоминание, чей момент уже прошёл (после смены пояса или включения), не отправляется задним числом.
- Исполнение: тик pg-boss каждые 5 минут выбирает `nextFireAt <= now()` и `enabled`, батч до 500, `FOR UPDATE SKIP LOCKED`. Проверяет связь active, отсутствие факта за день, паузу и лимит 2 push в сутки (NFR-LIMIT-013). Отправляет, пишет `lastSentLocalDate`, пересчитывает `nextFireAt`.
- Почему не задача pg-boss на напоминание: при смене пояса или DST пришлось бы отменять и пересоздавать задачи, это источник гонок. Тик с индексом проще. Точность ±5 мин (допущение).

**DST и смена пояса.**

| Случай | Правило |
|---|---|
| Пропущенный час (весна; 02:30 не существует) | сдвиг вперёд: 02:30 → 03:00 местного |
| Повторяющийся час (осень; 02:30 дважды) | одна отправка, в первом вхождении |
| Напоминание 07:00 | местное время сохраняется, UTC меняется на час |
| Смена пояса | пересчёт `nextFireAt`; `lastSentLocalDate` не сбрасывается, если дата та же |
| Путешествие (устройство в другом поясе) | вопрос «Перейти на [пояс]?» (FR-NOTIF-104); без «Да» профиль не меняется |

**Когда приходят уведомления: server push или локальные.**

| Критерий | Server push (FCM/APNs через `PushProvider`) | Локальные на устройстве |
|---|---|---|
| Знает текущее состояние (пауза, отвязка, выполнено на другом устройстве) | да, проверка при отправке | нет, устаревает |
| Отмена при отвязке (FR-NOTIF-003, -107) | сервер не отправит | только при открытии приложения, не гарантировано |
| Пересчёт при смене пояса | сервер | приложение, только если открыто |
| Приватность и вендор | текст на сервере без PII (NFR-PRIV-001); нужны DPA и регион FCM/APNs (NFR-PRIV-004) | текст лежит на устройстве; вендора нет |

**Рекомендация (предложено, ADR):** server push — единственный канал напоминаний и событий связи. Локальные уведомления в MVP не используются: отмену при паузе или отвязке и пересчёт DST на устройстве не выполнить надёжно. Баннер в приложении (FR-NOTIF-101) остаётся запасным путём. Expo Push Service отклонён до проверки региона (CLAUDE §3 задаёт FCM/APNs через `PushProvider`).

**Тихие часы и лимиты (предложено, утвердить).** Тихие часы 22:00–07:00 местного; окно короче 6 часов недопустимо. Напоминания о тренировке задаются в окне 05:00–22:00 (по умолчанию 07:00). Статусные push вне тихих часов переносятся на 07:00 местного. Не более 2 push в сутки на пользователя (NFR-LIMIT-013).

**Доставка, повторы, дедупликация, содержимое.**
- Best-effort: FCM и APNs не гарантируют доставку. Приложение не считает push единственным источником (FR-NOTIF-101).
- Повторы: 3 попытки с экспоненциальной задержкой на транспортные ошибки (NFR-REL-008). `UNREGISTERED` или `404` — удалить токен без повтора. TTL: 2 часа для напоминаний, 24 часа для статусов связи (предложено).
- Collapse key: HMAC от `reminderId + localDate`, усечённый до 64 байт (ограничение `apns-collapse-id`). Сырые ID не передаются. Серверная дедупликация: `lastSentLocalDate` и `singletonKey` pg-boss (проверить версию).
- Текст из фиксированного набора («Пора заниматься», «Не забудьте отметить тренировку»). Без имени, веса, упражнения и имени тренера (FR-NOTIF-105, NFR-PRIV-001). Payload: только тип (`reminder`, `plan_changed`, `link_changed`) и collapse key; тест схемы отклоняет любой ID клиента.

**Отказ в разрешении и токены устройств.** Отказ: баннер «Включить уведомления» на «Сегодня» и экран S12 (FR-NOTIF-101). Напоминание на сервере не создаётся, «Включено» не показывается. Токены: одна запись на устройство (`deviceId`, `token`, `platform`, `lastSeenAt`), ротация при запуске, если токен изменился (`onTokenRefresh`). Удаление: при выходе (в том же запросе logout), при отзыве сессии, при `UNREGISTERED`, после 60 дней без входа (BR-DATA-005), при удалении аккаунта (BR-DATA-006). Токен не логируется (NFR-PRIV-002).

**Примеры с точным UTC.** Напоминание 07:00 местного; дата тренировки — локальная.

| Кейс | Местное время | UTC | Комментарий |
|---|---|---|---|
| Berlin, зима, 2026-12-01 07:00 | CET, UTC+1 | 2026-12-01T06:00:00Z | |
| Berlin, лето, 2026-07-01 07:00 | CEST, UTC+2 | 2026-07-01T05:00:00Z | |
| Berlin, 2026-03-29 07:00 (день перехода) | CEST | 2026-03-29T05:00:00Z | переход в 01:00Z |
| Berlin, 2026-10-25 07:00 (день осеннего перехода) | CET | 2026-10-25T06:00:00Z | переход в 01:00Z |
| Berlin, 2026-03-29 02:30 (пропущенный час) | не существует | 2026-03-29T01:00:00Z | сдвиг до 03:00 CEST |
| Berlin, 2026-10-25 02:30 (повторяющийся час) | два вхождения | 2026-10-25T00:30:00Z | одна отправка |
| Тренер в Lisbon, клиент Berlin, 2026-12-01 07:00 | CET | 2026-12-01T06:00:00Z | тренер видит пояс клиента |
| Berlin: конец дня 2026-12-01 (пропуск не раньше) | 2026-12-02 00:00 CET | 2026-12-01T23:00:00Z | BR-DATE-002 |

**Тесты времени.** Unit в `packages/domain`: границы полуночи (Berlin, Lisbon, Tokyo, Los Angeles); `nextFireAt` на переходах 2026-03-29, 2026-10-25, 2027-03-28 (Berlin) и 2026-03-08, 2026-11-01 (New York). Integration: смена пояса не меняет `CalendarEntry.date` (NFR-I18N-004). Job: тик не отправляет дважды за локальный день и не отправляет после отвязки (FR-NOTIF-003). `Intl` с `timeZone` на Hermes — отдельно на устройстве.

## 6. Открытые вопросы

- **OQ-1 Офлайн-план против ст. 9.** FR-CAL-102 противоречит FR-CAL-109 и ст. 9. Варианты: (а) без офлайн-плана в MVP, FR-CAL-102 переписать (рекомендовано); (б) зашифрованный SQLite без полей здоровья. Нужны решение владельца и DPIA.
- **OQ-2 Push-вендор.** Прямой FCM/APNs (рекомендовано) или Expo Push. Для второго нужны DPA и регион.
- **OQ-3 Тихие часы, окно напоминаний, лимит 2 push.** Утвердить; решить, учитывать ли статусные push отдельно.
- **OQ-4 Права на видео и источник загрузки** (платформа или тренер). Блокирует BL-PERF-07 и -08.
- **OQ-5 CDN и логи.** IP в логах CDN — персональные данные; нужна политика маскирования.
- **OQ-6 Reduce motion.** Подтвердить как продуктовое требование: WCAG 2.3.3 относится к AAA.
- **OQ-7 Приоритет напоминаний.** FR-NOTIF-102 (Must, EPIC-4) и FR-NOTIF-004 (Should, EPIC-6) расходятся.
- **OQ-8 Непроверенные допущения.** `Intl` с `timeZone` на Hermes; частота открытий (2 в сутки); доля видео (20%); silent push с типом без ID на iOS в фоне. Уточнить на устройстве и на закрытой бете.
