# 12. Функциональные требования: общие части и админка

Дата: 2026-11-23. Источник правил: `noexcuse/CLAUDE.md` (§5, §6, §9), `План MVP v1.1` (§2.3, §3, §5, §6), `00-validation.md` (решения O1–O8 приняты как рекомендованные).

## 0. Соглашения

- **EPIC-N** = этап N плана (раздел 3): EPIC-1 связь тренер–клиент · EPIC-2 план и календарь · EPIC-3 факт и питание · EPIC-4 готовность к бете · EPIC-5 закрытая бета · EPIC-6 остальной MVP · EPIC-7 публичный запуск.
- **[O#]** — требование зависит от открытого решения владельца; при другом решении меняется одно правило, указанное в `00-validation.md` раздел 6.
- **Ошибки** — RFC 9457 (`{type, title, status, code, detail, requestId, errors[]}`). Коды без пометки существуют в `packages/contracts/src/errors.ts`. Код с пометкой **(новый)** добавляется в контракт (contract-first) до реализации.
- **Экран** — название словами; «нет (API)» для требований без пользовательского экрана.
- Все негативные состояния приглашения возвращают один ответ (см. FR-LINK-004), клиентский код ветвится по `code`, не по тексту.
- Тренер и клиент — роли одного мобильного приложения; персонал — роли веб-админки.

## 1. Общая аутентификация (FR-AUTH)

### FR-AUTH-001 Вход через Apple, Google и email
**Актор:** Клиент, Тренер, Персонал
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** приложение установлено; активной сессии нет; OIDC-провайдер в регионе ЕС доступен через адаптер `AuthProvider`.
**Описание:** вход выполняется через managed OIDC за адаптером `AuthProvider`. API проверяет JWT по JWKS и не хранит пароли. Токены хранятся только в `expo-secure-store`. Первый вход без профиля переводит на экран создания профиля.
**Критерии приёмки:**
- Дано: новый пользователь выбрал «Войти через Apple», Когда OIDC вернул валидный токен, Тогда создана сессия, и пользователь без профиля переходит на экран профиля (ответ `PROFILE_REQUIRED`).
- Дано: токен с неверной подписью или истёкший, Когда запрос уходит на `/v1`, Тогда ответ 401 `UNAUTHENTICATED`, данные не возвращаются, токен не сохраняется.
**Ошибки:** 401 `UNAUTHENTICATED`; 503 (новый) `AUTH_PROVIDER_UNAVAILABLE` при недоступности OIDC.
**Экран:** Вход
**Связи:** BR-DATA-008, BR-DATA-010

### FR-AUTH-002 Sign in with Apple обязателен при социальном входе
**Актор:** Система (релиз-чеклист), Клиент, Тренер
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** в приложении доступен вход через Google.
**Описание:** на iOS вход через Google доступен только вместе со входом через Apple. Требование store-ревью (`CLAUDE.md` §3).
**Критерии приёмки:**
- Дано: сборка iOS с Google-входом, Когда пользователь открывает экран входа, Тогда кнопка Sign in with Apple показана не ниже кнопки Google.
- Дано: сборка без Sign in with Apple, Когда выполняется релиз-чеклист, Тогда релиз блокируется (проверка в CI-шаге сборки).
**Ошибки:** нет (проверка на уровне сборки и релиз-чеклиста).
**Экран:** Вход
**Связи:** BR-DATA-008

### FR-AUTH-003 Выход
**Актор:** Клиент, Тренер, Персонал
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** пользователь аутентифицирован.
**Описание:** выход удаляет токены из secure storage на устройстве и отзывает refresh-токен на сервере. Кэш запросов очищается, персональные данные из памяти удаляются.
**Критерии приёмки:**
- Дано: пользователь в сети, Когда нажимает «Выйти», Тогда сервер отзывает сессию (204), токены удалены, открыт экран входа.
- Дано: нет сети, Когда нажимает «Выйти», Тогда токены и кэш на устройстве удалены немедленно; отзыв на сервере выполняется при следующем подключении, и выход не показывается как «ошибка».
**Ошибки:** 401 `UNAUTHENTICATED` (игнорируется клиентом, локальная очистка выполняется в любом случае).
**Экран:** Настройки профиля
**Связи:** BR-DATA-008

### FR-AUTH-004 Обновление токена: одна попытка, затем выход
**Актор:** Клиент, Тренер, Персонал
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** есть refresh-токен; запрос вернул 401.
**Описание:** при 401 клиент делает ровно одну попытку обновления токена. Если она не удалась, выполняется локальный выход (`CLAUDE.md` §6). Параллельные запросы ждут одну попытку, а не запускают несколько.
**Критерии приёмки:**
- Дано: access-токен истёк, refresh валиден, Когда запрос вернул 401, Тогда выполнена одна попытка refresh, исходный запрос повторён один раз и вернул данные.
- Дано: refresh отозван, Когда запрос вернул 401, Тогда выполнен локальный выход без повторных попыток и цикла запросов; показано сообщение «Войдите снова».
**Ошибки:** 401 `UNAUTHENTICATED`.
**Экран:** нет (API и клиентский слой); при неуспехе — Вход
**Связи:** BR-DATA-008

### FR-AUTH-005 Выбор роли: только «Я тренер» или вход по коду клиента [O1]
**Актор:** Новый пользователь
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** пользователь аутентифицирован, профиля нет.
**Описание:** при создании профиля доступны два пути: «Я тренер» или «У меня есть код тренера» (ввод инвайта). Выбор «я пользователь без тренера» отсутствует. Один аккаунт — одна роль; тренер, который тренируется сам, заводит второй аккаунт [O1]. Роль фиксируется при создании профиля.
**Критерии приёмки:**
- Дано: новый пользователь на шаге роли, Когда выбирает «Я тренер», Тогда создан профиль тренера, роль — `coach`, и открыт онбординг тренера.
- Дано: пользователь без кода, Когда пытается продолжить как клиент, Тогда экран «Нужен код тренера» без создания профиля; профиль клиента не создан (`PROFILE_REQUIRED`).
**Ошибки:** 409 `PROFILE_EXISTS`; 422 `VALIDATION_FAILED`; 403 `FORBIDDEN_ROLE` при попытке сменить роль существующего аккаунта.
**Экран:** Выбор роли; Ввод кода тренера
**Связи:** BR-INVITE-001, BR-LINK-001

### FR-AUTH-006 MFA для тренера
**Актор:** Тренер
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** профиль тренера создан.
**Описание:** тренер обязан подключить второй фактор до первого доступа к клиентам. Без MFA доступны только онбординг и настройки второго фактора. Причина: тренер видит данные здоровья клиентов.
**Критерии приёмки:**
- Дано: тренер без MFA, Когда открывает список клиентов, Тогда API отвечает 403 `MFA_REQUIRED` (новый), приложение открывает настройку второго фактора.
- Дано: тренер подключил MFA и подтвердил код, Когда открывает список клиентов, Тогда список возвращён, сессия содержит подтверждение второго фактора.
**Ошибки:** 403 `MFA_REQUIRED` (новый); 401 `UNAUTHENTICATED`.
**Экран:** Безопасность аккаунта; Список клиентов
**Связи:** BR-DATA-010

### FR-AUTH-007 Восстановление аккаунта
**Актор:** Клиент, Тренер
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** аккаунт существует; пользователь потерял доступ к способу входа.
**Описание:** восстановление через повторный вход тем же OIDC-провайдером или по email, привязанному к аккаунту. Восстановление не даёт доступа к данным без проверки личности: сброс второго фактора тренера требует подтверждения по email и задержки 24 ч с уведомлением на прежний email.
**Критерии приёмки:**
- Дано: клиент вошёл с тем же email, Когда подтверждает восстановление, Тогда аккаунт открыт с прежними связями и согласиями.
- Дано: попытка сброса MFA тренера без подтверждения по email, Когда запрос отправлен, Тогда сброс не выполнен, уведомление отправлено на прежний email.
**Ошибки:** 401 `UNAUTHENTICATED`; 429 `RATE_LIMITED`.
**Экран:** Восстановление доступа
**Связи:** BR-DATA-010

### FR-AUTH-008 Утрата телефона (второй фактор)
**Актор:** Тренер, Персонал
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** MFA подключён; устройство с вторым фактором утеряно.
**Описание:** резервные коды выдаются при подключении MFA и показываются один раз. Если резервных кодов нет, сброс проходит по FR-AUTH-007 с задержкой 24 ч. Персонал восстанавливается только через другого super_admin.
**Критерии приёмки:**
- Дано: тренер ввёл резервный код, Когда код не использован, Тогда вход выполнен, код помечен использованным.
- Дано: тот же резервный код повторно, Когда введён, Тогда отказ 401 `UNAUTHENTICATED`, одна попытка не даёт второй.
**Ошибки:** 401 `UNAUTHENTICATED`; 429 `RATE_LIMITED`.
**Экран:** Второй фактор; Восстановление доступа
**Связи:** BR-DATA-010

## 2. Аккаунт, профиль и данные (FR-ACCT)

### FR-ACCT-001 Профиль и часовой пояс
**Актор:** Клиент, Тренер
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** пользователь аутентифицирован.
**Описание:** профиль содержит отображаемое имя (до 80 символов) и часовой пояс IANA. Часовой пояс обязателен: даты тренировок и пропуски считаются в нём (`CLAUDE.md` §6). Часовой пояс определяется устройством как подсказка, но подтверждается пользователем.
**Критерии приёмки:**
- Дано: новый клиент, Когда выбирает часовой пояс `Europe/Berlin` и сохраняет, Тогда профиль сохранён, ответ содержит TZ, даты календаря считаются в нём.
- Дано: часовой пояс `Mars/Olympus`, Когда отправлен, Тогда отказ 422 `VALIDATION_FAILED` с `errors[].path = timezone`.
**Ошибки:** 422 `VALIDATION_FAILED`; 409 `PROFILE_EXISTS`.
**Экран:** Профиль; Онбординг
**Связи:** BR-DATE-001, BR-DATE-003

### FR-ACCT-002 Экспорт данных (машиночитаемо, ≤1 месяц)
**Актор:** Клиент, Тренер
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** пользователь аутентифицирован.
**Описание:** экспорт формирует JSON по контракту `AccountExportSchema`: профиль, согласия, связи, свои инвайты без кодов и хэшей, план связей клиента, записи календаря. Экспорт готов не позже 1 месяца от запроса, в типичном случае — минуты. Ссылка на файл временная (signed URL, 24 ч), файл шифруется at rest.
**Критерии приёмки:**
- Дано: клиент запросил экспорт, Когда генерация завершена, Тогда доступен JSON, валидный по `AccountExportSchema`, содержит согласия и записи календаря.
- Дано: запрос экспорта от пользователя без аутентификации, Когда отправлен, Тогда отказ 401, файл не формируется. Дано: в экспорте не должно быть инвайт-кодов и хэшей.
**Ошибки:** 401 `UNAUTHENTICATED`; 429 `RATE_LIMITED`; 500 `INTERNAL`.
**Экран:** Мои данные
**Связи:** BR-DATA-007, BR-DATA-005

### FR-ACCT-003 Удаление аккаунта с каскадом
**Актор:** Клиент, Тренер
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** пользователь аутентифицирован; пользователь подтвердил удаление вводом слова из экрана и паролём/вторым фактором при наличии.
**Описание:** удаление необратимо. В одной транзакции удаляются: строки User, Consent, Invite, IdempotencyRecord, CalendarEntry, PlanVersion, а связи переходят в ended, у второй стороны сохраняется история. Затем каскад: бэкапы (по истечении ротации, не позже срока BR-DATA-006), Sentry (удаление по ID субъекта), push-токены, файлы экспорта. Срок полного удаления — не более 1 месяца.
**Критерии приёмки:**
- Дано: клиент подтвердил удаление, Когда транзакция завершена, Тогда аккаунт недоступен для входа, связь с тренером ended, его доступ закрыт, запись в журнале удаления создана без PII.
- Дано: запрос удаления без подтверждения второго шага, Когда отправлен, Тогда отказ 422 `VALIDATION_FAILED`, данные не изменены.
**Ошибки:** 422 `VALIDATION_FAILED`; 401 `UNAUTHENTICATED`; 409 `VERSION_CONFLICT` при параллельном изменении связи.
**Экран:** Удаление аккаунта
**Связи:** BR-DATA-006, BR-LINK-009, BR-LINK-010

### FR-ACCT-004 Удаление тренера и судьба связей
**Актор:** Тренер, Система
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** у тренера есть связи active или paused.
**Описание:** при удалении тренера все его открытые связи переводятся в ended с `endedBy=coach`. Клиент видит связь как ended с пустым тренером (`coachDisplayName=null`) и сохраняет историю. Будущие записи календаря и напоминания снимаются. Клиент может сразу привязаться к новому тренеру (новый инвайт).
**Критерии приёмки:**
- Дано: тренер с тремя клиентами удалён, Когда транзакция завершена, Тогда все три связи ended, доступ тренера закрыт, у клиентов сохранена история.
- Дано: клиент после удаления тренера, Когда открывает свою связь, Тогда видит ended-связь без имени тренера, а не ошибку; новый тренер через инвайт привязывается.
**Ошибки:** нет (внутренняя операция); при сбое транзакции 500 `INTERNAL`.
**Экран:** Мой тренер (состояние «тренер удалён»)
**Связи:** BR-LINK-011, BR-LINK-009, BR-LINK-010

### FR-ACCT-005 Возрастной гейт 18+
**Актор:** Клиент, Тренер
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** начало регистрации.
**Описание:** при регистрации пользователь подтверждает, что ему 18 лет и более (самодекларация, дата рождения не хранится). Без подтверждения регистрация не продолжается. Юр-пакет (ToS) подписан до беты [юр. пакет, этап 4].
**Критерии приёмки:**
- Дано: пользователь отметил «мне 18 лет и больше», Когда продолжает регистрацию, Тогда шаг возрастного гейта сохранён как факт, профиль создаётся.
- Дано: пользователь отметил «мне меньше 18», Когда продолжает, Тогда регистрация прекращена, аккаунт не создаётся, показан нейтральный текст без сбора данных.
**Ошибки:** 403 `FORBIDDEN_ROLE` (возрастной отказ, с нейтральным текстом); 422 `VALIDATION_FAILED`.
**Экран:** Возрастной гейт
**Связи:** BR-CONSENT-001, BR-SAFETY-002

### FR-ACCT-006 Смена часового пояса
**Актор:** Клиент, Тренер
**Приоритет и этап:** Must, EPIC-6
**Предусловия:** профиль существует.
**Описание:** при смене TZ даты записей календаря не сдвигаются; пересчитываются только моменты напоминаний. Пропуски считаются по новому дню в новом поясе. Причина: `DATE` хранится как локальная дата (`CLAUDE.md` §6).
**Критерии приёмки:**
- Дано: клиент с тренировкой на 2026-12-01 в `Europe/Berlin`, Когда меняет TZ на `Asia/Tokyo`, Тогда тренировка остаётся на 2026-12-01, напоминание пересчитано на 07:00 нового пояса.
- Дано: смена TZ на невалидный пояс, Когда отправлена, Тогда отказ 422 `VALIDATION_FAILED`, напоминания не пересчитаны.
**Ошибки:** 422 `VALIDATION_FAILED`.
**Экран:** Профиль
**Связи:** BR-DATE-003, BR-DATE-004

## 3. Связи, инвайты и согласия (FR-LINK, серверная часть)

### FR-LINK-001 Создание инвайта
**Актор:** Тренер
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** тренер аутентифицирован, MFA подключён (FR-AUTH-006), онбординг пройден.
**Описание:** инвайт — случайный код не менее 128 бит (CSPRNG), кодировка Crockford base32 длиной 26 символов. В БД хранится только SHA-256 хэш; код показывается тренеру один раз. TTL — 168 ч от создания, одноразовый.
**Критерии приёмки:**
- Дано: тренер с MFA, Когда создаёт инвайт, Тогда ответ 201 с кодом, `expiresAt = createdAt + 168 ч`, в БД строка с `codeHash` и без кода.
- Дано: тренер без MFA, Когда создаёт инвайт, Тогда отказ 403 `MFA_REQUIRED`, запись не создана.
**Ошибки:** 201 успех; 403 `MFA_REQUIRED`; 429 `RATE_LIMITED`; 422 `VALIDATION_FAILED`.
**Экран:** Пригласить клиента
**Связи:** BR-INVITE-001, BR-INVITE-002, BR-INVITE-003

### FR-LINK-002 Лимит создания инвайтов
**Актор:** Тренер, Система
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** тренер аутентифицирован.
**Описание:** не более 5 созданных инвайтов в час на тренера. Превышение блокирует создание до конца окна. Счётчик атомарный в Postgres (`RateLimitHit`), работает при нескольких инстансах API.
**Критерии приёмки:**
- Дано: тренер создал 5 инвайтов за час, Когда создаёт шестой, Тогда ответ 429 `RATE_LIMITED`, инвайт не создан, заголовок `Retry-After` указывает окончание окна.
- Дано: тренер создал 4 инвайта за час, Когда создаёт пятый, Тогда ответ 201.
**Ошибки:** 429 `RATE_LIMITED`.
**Экран:** Пригласить клиента (сообщение «Лимит на час исчерпан»)
**Связи:** BR-INVITE-008

### FR-LINK-003 Погашение инвайта атомарно
**Актор:** Клиент
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** пользователь аутентифицирован с профилем клиента; введён код; обязательные согласия отмечены в текущих версиях.
**Описание:** погашение — одна условная операция UPDATE: инвайт не использован, не отозван, не истёк. Одновременные запросы с одним кодом: успешен ровно один. При успехе создаётся связь `active` и согласия, привязанные к связи (FR-LINK-012).
**Критерии приёмки:**
- Дано: валидный код, Когда два клиента отправляют погашение одновременно, Тогда один получает 201 со связью, второй получает 404 `INVITE_INVALID`; в БД ровно одна связь.
- Дано: клиент, у которого уже есть открытая связь, Когда погашает другой валидный код, Тогда отказ 409 `LINK_EXISTS`, инвайт не помечен использованным.
**Ошибки:** 201 успех; 404 `INVITE_INVALID`; 409 `LINK_EXISTS`; 422 `CONSENT_REQUIRED`.
**Экран:** Ввод кода тренера; Согласие на связь
**Связи:** BR-INVITE-004, BR-INVITE-007, BR-LINK-002

### FR-LINK-004 Единый ответ 404 на любое негативное состояние инвайта
**Актор:** Клиент (и любой анонимный вызывающий)
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** код передан на погашение или проверку.
**Описание:** несуществующий, истёкший, использованный, отозванный или чужой код возвращают одинаковый ответ 404 с кодом `INVITE_INVALID` и одинаковым текстом. Время ответа не различает состояния (проверка по единому пути). Причина: защита от перебора и утечки состояний.
**Критерии приёмки:**
- Дано: истёкший код, Когда погашается, Тогда ответ 404 `INVITE_INVALID` с текстом, идентичным ответу для несуществующего кода.
- Дано: несуществующий код, Когда погашается, Тогда ответ 404 `INVITE_INVALID`, тело совпадает с ответом для истёкшего кода (контрактный тест сравнивает тела).
**Ошибки:** 404 `INVITE_INVALID`.
**Экран:** Ввод кода тренера (сообщение «Код недействителен»)
**Связи:** BR-INVITE-005

### FR-LINK-005 Rate-limit погашения по IP и коду
**Актор:** Система, Клиент
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** запрос на погашение.
**Описание:** не более 5 попыток погашения за 10 минут отдельно по IP-адресу клиента и по значению кода. Превышение возвращает 429 независимо от правильности кода. Лимиты в Postgres, одинаковы для всех инстансов.
**Критерии приёмки:**
- Дано: с одного IP 5 попыток с неверным кодом за 10 минут, Когда приходит шестая, Тогда ответ 429 `RATE_LIMITED`, даже если код верный.
- Дано: 4 попытки с одного IP, Когда приходит пятая с верным кодом, Тогда погашение выполнено.
**Ошибки:** 429 `RATE_LIMITED`.
**Экран:** Ввод кода тренера (сообщение «Слишком много попыток, попробуйте через 10 минут»)
**Связи:** BR-INVITE-009

### FR-LINK-006 Жизненный цикл связи: active, paused, ended
**Актор:** Тренер, Клиент, Система
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** связь существует.
**Описание:** связь в одном из статусов active, paused, ended. Переходы — только по матрице `LINK_TRANSITIONS`: pause и resume — тренер; end — тренер или клиент (админ — FR-ADM-011). Ended терминален. Неизвестный статус в ответе клиент читает как `unknown`, доступ при этом закрыт (BR-LINK-004).
**Критерии приёмки:**
- Дано: связь active, Когда тренер ставит паузу, Тогда статус paused, ответ 200 с новым статусом.
- Дано: связь ended, Когда тренер пытается resume, Тогда отказ 409 `INVALID_TRANSITION`, статус не меняется.
**Ошибки:** 409 `INVALID_TRANSITION`; 404 `NOT_FOUND` (чужая связь); 409 `VERSION_CONFLICT`.
**Экран:** Карточка клиента; Мой тренер
**Связи:** BR-LINK-006, BR-LINK-004, BR-LINK-008

### FR-LINK-007 Одна открытая связь на клиента [O2]
**Актор:** Система
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** клиент имеет связь active или paused.
**Описание:** клиент не может иметь двух тренеров одновременно: одна связь в статусах active или paused на клиента. Гарантируется ограничением в БД (миграция), не только проверкой в коде. Повторный инвайт от другого тренера при открытой связи отклоняется.
**Критерии приёмки:**
- Дано: клиент с активной связью с тренером A, Когда погашает инвайт тренера B, Тогда отказ 409 `LINK_EXISTS`.
- Дано: параллельная вставка второй открытой связи минуя сервис, Когда выполняется SQL, Тогда отказ ограничения БД.
**Ошибки:** 409 `LINK_EXISTS`.
**Экран:** Ввод кода тренера (сообщение «У вас уже есть тренер»)
**Связи:** BR-LINK-002

### FR-LINK-008 Пауза: доступ тренера не закрывается [O3]
**Актор:** Клиент, Тренер
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** связь active.
**Описание:** пауза (связь paused) не закрывает доступ тренера к данным клиента. Она отключает напоминания и учёт пропусков. Клиент ставит «пауза/болезнь», тренер подтверждает. Решение [O3]: рекомендация 00-validation, в `link.ts` правило `pause` меняется (K6). Пауза доступна клиенту (запрос) и тренеру (прямое действие); прямая пауза тренером требует уведомления клиенту.
**Критерии приёмки:**
- Дано: связь paused, Когда тренер запрашивает карточку клиента, Тогда доступ разрешён (200), пропуски не начисляются, напоминания выключены.
- Дано: клиент запросил паузу, Когда тренер не подтвердил, Тогда связь остаётся active, напоминания продолжаются.
**Ошибки:** 409 `INVALID_TRANSITION`; 404 `NOT_FOUND`.
**Экран:** Пауза (клиент); Карточка клиента (тренер)
**Связи:** BR-LINK-005, BR-LINK-006

### FR-LINK-009 Отвязка закрывает доступ немедленно
**Актор:** Клиент, Тренер
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** связь active или paused.
**Описание:** отвязка (end) в одной транзакции: статус ended, `endedAt`, `endedBy`; будущие записи календаря и запланированные напоминания удаляются; история (факт, план версии, согласия) остаётся у клиента. Со следующего запроса тренер получает 404 на данные клиента, без задержки кэша.
**Критерии приёмки:**
- Дано: тренер и клиент связаны, у клиента 10 будущих записей, Когда клиент отвязывает тренера, Тогда связь ended, будущие записи удалены, история доступна клиенту.
- Дано: тренер запрашивает карточку клиента сразу после отвязки, Когда запрос выполнен, Тогда ответ 404 `NOT_FOUND`, данные не возвращаются.
**Ошибки:** 409 `INVALID_TRANSITION`; 404 `NOT_FOUND`.
**Экран:** Мой тренер (отвязка); Карточка клиента (тренер видит «связь завершена»)
**Связи:** BR-LINK-007, BR-LINK-009, BR-LINK-010

### FR-LINK-010 Отзыв согласия как событие с каскадом
**Актор:** Клиент
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** согласие выдано.
**Описание:** отзыв — новая запись согласия с `granted=false` (история не переписывается). Отзыв `coach_access` завершает связь (каскад как при отвязке, BR-LINK-009). Отзыв `health_data` закрывает доступ тренера к данным здоровья (замеры, факт питания), связь остаётся. Отзыв `marketing` влияет только на рассылки.
**Критерии приёмки:**
- Дано: клиент с согласием `coach_access`, Когда отзывает его, Тогда связь ended, доступ тренера закрыт, событие записано в журнал согласий.
- Дано: клиент отозвал `health_data`, Когда тренер запрашивает замеры, Тогда отказ 404 `NOT_FOUND`, а карточка с целью остаётся доступна.
**Ошибки:** 422 `VALIDATION_FAILED`; 409 `VERSION_CONFLICT`.
**Экран:** Согласия и данные
**Связи:** BR-CONSENT-004, BR-CONSENT-006, BR-CONSENT-009

### FR-LINK-011 Смена версии согласия: переподтверждение [K5]
**Актор:** Клиент, Система
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** опубликована новая версия текста согласия (`CONSENT_VERSIONS` изменена).
**Примечание:** в клиентской части экран «Переподтверждение» обязателен до выпуска версии; `CONSENT_REQUIRED` возвращается клиенту при попытке использовать связь без подтверждения, когда API отвечает на действие клиента, а не на запрос тренера.
**Описание:** при смене версии доступ, опирающийся на устаревшую версию, не отключается молча. Клиенту показывается экран переподтверждения текста; до подтверждения доступ тренера закрыт, и экран объясняет причину. Старые записи не меняются. Поток обязателен перед релизом новой версии.
**Критерии приёмки:**
- Дано: версия `coach_access` изменена, Когда клиент открывает приложение, Тогда показан экран переподтверждения с новым текстом, а не молчаливое отключение.
- Дано: клиент не подтвердил новую версию, Когда тренер запрашивает данные клиента, Тогда ответ 404 `NOT_FOUND` (без раскрытия причины), тренер видит «Данные недоступны».
**Ошибки:** 422 `CONSENT_REQUIRED`; 422 `VALIDATION_FAILED` при неверной версии.
**Экран:** Переподтверждение согласий
**Связи:** BR-CONSENT-007, BR-CONSENT-003

### FR-LINK-012 Раздельные согласия при погашении инвайта
**Актор:** Клиент
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** клиент вводит валидный код.
**Описание:** при погашении клиент даёт раздельные согласия: `tos`, `health_data`, `coach_access` обязательны, `marketing` необязательно и по умолчанию выключено. Каждое согласие сохраняется записью, привязанной к связи (не к пользователю). Отказ от обязательного согласия — связь не создаётся, инвайт не расходуется.
**Критерии приёмки:**
- Дано: клиент отметил три обязательных согласия в текущих версиях, Когда погашает код, Тогда связь создана, три записи согласий содержат `linkId`, `marketing` отсутствует или `granted=false`.
- Дано: клиент снял галочку `health_data`, Когда отправляет, Тогда отказ 422 `CONSENT_REQUIRED`, инвайт остаётся валидным, связь не создана.
**Ошибки:** 422 `CONSENT_REQUIRED`; 422 `VALIDATION_FAILED`.
**Экран:** Согласие на связь с тренером
**Связи:** BR-CONSENT-001, BR-CONSENT-002, BR-CONSENT-005

## 4. Администрирование (FR-ADM)

Веб-админка `apps/admin` (Refine + React) поверх `/v1` и `packages/contracts`. Для беты действует Admin-lite [O4]: отзыв связи, экспорт/удаление и аудит (FR-ADM-004, FR-ADM-005, FR-ADM-007, FR-ADM-010); полная админка — к запуску.

### FR-ADM-001 Вход персонала с MFA
**Актор:** Персонал
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** учётная запись персонала создана super_admin.
**Описание:** персонал входит через тот же OIDC с отдельной ролью персонала. MFA обязателен для всех ролей и проверяется при каждом входе в админку. Учётная запись персонала не может быть связана с клиентским или тренерским профилем.
**Критерии приёмки:**
- Дано: сотрудник с ролью support и подтверждённым MFA, Когда входит в админку, Тогда доступ к списку пользователей открыт по его роли.
- Дано: сотрудник без MFA, Когда пытается войти, Тогда отказ 403 `MFA_REQUIRED` (новый), админка не открывается.
**Ошибки:** 403 `MFA_REQUIRED` (новый); 401 `UNAUTHENTICATED`; 403 `FORBIDDEN_ROLE`.
**Экран:** Вход в админку
**Связи:** BR-DATA-010

### FR-ADM-002 RBAC: роли support, verifier, moderator, auditor, super_admin
**Актор:** Персонал
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** персонал аутентифицирован (FR-ADM-001).
**Описание:** права по ролям: support — список, отзыв связи, запросы экспорта/удаления; verifier — верификация тренеров (к запуску); moderator — модерация (Should); auditor — чтение аудит-лога и метрик, без доступа к персональным данным; super_admin — назначение ролей и все права. Данные здоровья не доступны ни одной роли по умолчанию (FR-ADM-006). Принцип наименьших прав (`CLAUDE.md` §9).
**Критерии приёмки:**
- Дано: роль auditor, Когда открывает список пользователей, Тогда ответ 403 `FORBIDDEN_ROLE`.
- Дано: роль support, Когда пытается верифицировать тренера, Тогда ответ 403 `FORBIDDEN_ROLE`, действие не выполнено.
**Ошибки:** 403 `FORBIDDEN_ROLE`; 404 `NOT_FOUND` для объекта вне прав.
**Экран:** Управление ролями персонала
**Связи:** BR-DATA-009

### FR-ADM-003 Список пользователей и связей: только метаданные
**Актор:** Персонал (support, auditor)
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** персонал с правом чтения.
**Описание:** списки показывают: id, роль, статус аккаунта, дата создания, статус связи, даты, endedBy. Имя, email, часовой пояс и любые данные здоровья не показываются; поиск по id или по выделенному тикету. Списки пагинируются курсором (лимит 20, максимум 100).
**Критерии приёмки:**
- Дано: support открывает список связей, Когда список загружен, Тогда в ответе нет полей `displayName`, `timezone`, данных плана и согласий.
- Дано: запрос с `limit=500`, Когда отправлен, Тогда отказ 422 `VALIDATION_FAILED` или ограничение до 100.
**Ошибки:** 422 `VALIDATION_FAILED`; 403 `FORBIDDEN_ROLE`.
**Экран:** Пользователи и связи
**Связи:** BR-DATA-008, BR-DATA-009

### FR-ADM-004 Отзыв связи и блокировка с причиной
**Актор:** Персонал (support, super_admin)
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** связь active или paused; у персонала есть права.
**Описание:** отзыв связи завершает её (ended, endedBy=admin) с каскадом FR-LINK-009. Блокировка аккаунта закрывает вход и доступ к данным. Обязательное поле «причина» (код из списка + текст до 500 символов без персональных данных). Действие пишется в аудит (FR-ADM-005).
**Критерии приёмки:**
- Дано: support с причиной «нарушение правил», Когда отзывает связь, Тогда связь ended, endedBy=admin, запись аудита создана, клиент и тренер получают уведомление без причины.
- Дано: попытка отзыва без причины, Когда отправлена, Тогда отказ 422 `VALIDATION_FAILED`, связь не изменена.
**Ошибки:** 422 `VALIDATION_FAILED`; 409 `INVALID_TRANSITION`; 403 `FORBIDDEN_ROLE`.
**Экран:** Карточка связи (админ)
**Связи:** BR-LINK-009, BR-LINK-006

### FR-ADM-005 Append-only аудит-лог
**Актор:** Система, Персонал (auditor)
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** любое действие персонала или доступ к чувствительным данным.
**Описание:** каждое действие персонала записывается: кто, роль, что, объект, причина, тикет, время, requestId. Таблица append-only: UPDATE и DELETE запрещены на уровне прав БД; очистка только по сроку хранения (BR-DATA-005). Аудит не содержит значений персональных данных и здоровья.
**Критерии приёмки:**
- Дано: support отозвал связь, Когда аудит прочитан auditor, Тогда есть запись с актором, объектом и причиной.
- Дано: попытка UPDATE записи аудита из приложения, Когда выполнена, Тогда ошибка прав БД, запись не меняется.
**Ошибки:** 403 `FORBIDDEN_ROLE`; 500 `INTERNAL` (при недоступности записи аудита действие отменяется).
**Экран:** Журнал аудита
**Связи:** BR-DATA-005, BR-DATA-009

### FR-ADM-006 Доступ к данным здоровья только по тикету с грантом
**Актор:** Персонал (support, super_admin)
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** открыт тикет поддержки с описанием задачи; у персонала есть право.
**Описание:** данные здоровья (замеры, план питания, факт) по умолчанию скрыты. Открываются временным грантом на 60 минут, привязанным к тикету и конкретной связи. Каждый просмотр пишется в аудит (FR-ADM-005). Грант нельзя продлить без нового тикета. Дополнительно: доступ не даётся, если согласие `health_data` клиента отозвано.
**Критерии приёмки:**
- Дано: тикет и грант на 60 минут, Когда support открывает замеры связи из тикета, Тогда данные показаны, просмотр записан в аудит с тикетом.
- Дано: грант истёк или тикет не привязан, Когда support запрашивает замеры, Тогда отказ 403 `FORBIDDEN_ROLE`, данные не возвращены.
**Ошибки:** 403 `FORBIDDEN_ROLE`; 404 `NOT_FOUND`.
**Экран:** Карточка связи — данные здоровья (по тикету)
**Связи:** BR-DATA-009, BR-CONSENT-009

### FR-ADM-007 Обработка запросов на экспорт и удаление
**Актор:** Персонал (support), Клиент
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** клиент отправил запрос на экспорт или удаление (FR-ACCT-002, FR-ACCT-003), либо запрос пришёл по почте/поддержке.
**Описание:** очередь запросов с дедлайном 1 месяц от поступления. Персонал видит тип, дату, дедлайн и статус без содержимого данных. Удаление выполняется сервисом (FR-ACCT-003), персонал подтверждает завершение каскада, включая бэкапы и Sentry. Просроченный запрос подсвечивается.
**Критерии приёмки:**
- Дано: запрос удаления за 25 дней до дедлайна, Когда открыта очередь, Тогда запрос в списке с оставшимися днями и статусом.
- Дано: запрос удаления закрыт без каскада в бэкапах, Когда персонал пытается отметить выполненным, Тогда отказ 422 `VALIDATION_FAILED` (каскад не подтверждён).
**Ошибки:** 422 `VALIDATION_FAILED`; 403 `FORBIDDEN_ROLE`.
**Экран:** Запросы клиентов
**Связи:** BR-DATA-006, BR-DATA-007

### FR-ADM-008 Верификация тренеров (к запуску)
**Актор:** Персонал (verifier), Тренер
**Приоритет и этап:** Must, EPIC-6 (к публичному запуску)
**Предусловия:** тренер подал заявку и загрузил подтверждающие документы; решение владельца о нужности верификации до запуска (план, раздел 7, п. 2).
**Описание:** очередь заявок. Решение «подтверждён» или «отклонён» с обязательной причиной. До верификации тренер может создавать инвайты только в режиме «на проверке» (см. открытый вопрос квалификации). Документы хранятся по сроку BR-DATA-005.
**Критерии приёмки:**
- Дано: verifier подтверждает заявку с причиной, Когда решение сохранено, Тогда статус тренера «верифицирован», запись аудита создана.
- Дано: verifier отклоняет заявку без причины, Когда отправлено, Тогда отказ 422 `VALIDATION_FAILED`.
**Ошибки:** 422 `VALIDATION_FAILED`; 403 `FORBIDDEN_ROLE`; 409 `VERSION_CONFLICT`.
**Экран:** Очередь верификации
**Связи:** BR-DATA-005, BR-DATA-009

### FR-ADM-009 Метрики воронки (к запуску)
**Актор:** Персонал (auditor, super_admin)
**Приоритет и этап:** Must, EPIC-6 (к публичному запуску)
**Предусловия:** события воронки собраны (аналитика ЕС, без данных здоровья).
**Описание:** агрегированные шаги воронки: установка → регистрация → связь → первый факт → первая неделя. Показываются только агрегаты (счётчики, без ID). Метрики гейта беты (BR-GATE-001) считаются тем же механизмом. Данные здоровья в аналитику не попадают.
**Критерии приёмки:**
- Дано: за неделю 10 связей и 7 фактов, Когда auditor открывает воронку, Тогда показаны агрегаты без идентификаторов.
- Дано: ячейка агрегата меньше порога k=5, Когда отображается, Тогда значение скрыто как «мало данных».
**Ошибки:** 403 `FORBIDDEN_ROLE`.
**Экран:** Воронка
**Связи:** BR-GATE-001, BR-GATE-003, BR-DATA-008

### FR-ADM-010 Admin-lite для беты [O4]
**Актор:** Персонал (super_admin)
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** бета запускается до полной админки.
**Описание:** минимальный набор до беты: вход с MFA (FR-ADM-001), отзыв связи (FR-ADM-004), обработка запросов экспорта и удаления (FR-ADM-007), аудит (FR-ADM-005). Полная админка (верификация, воронка, роли) — к запуску. Решение [O4]: Admin-lite; альтернатива runbook+скрипты не принята.
**Критерии приёмки:**
- Дано: super_admin в Admin-lite, Когда открывает разделы беты, Тогда доступны связи, запросы и аудит, и не доступны верификация и воронка.
- Дано: попытка использовать скрипт без записи в аудит, Когда выполнено, Тогда операция не выполнена (аудит обязателен).
**Ошибки:** 403 `FORBIDDEN_ROLE`; 500 `INTERNAL`.
**Экран:** Админка (Admin-lite)
**Связи:** BR-DATA-009, BR-LINK-009

### FR-ADM-011 Завершение связи администратором [K4]
**Актор:** Персонал (super_admin, support)
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** связь active или paused.
**Описание:** правило завершения связи (`end`) разрешено тренеру, клиенту и администратору. Сейчас `LINK_TRANSITIONS.end` содержит только `coach` и `client` (K4). Администратор завершает связь с причиной, как в FR-ADM-004.
**Критерии приёмки:**
- Дано: связь active, Когда администратор с правом support завершает её с причиной, Тогда статус ended, endedBy=admin.
- Дано: связь ended, Когда администратор пытается завершить её, Тогда отказ 409 `INVALID_TRANSITION`.
**Ошибки:** 409 `INVALID_TRANSITION`; 422 `VALIDATION_FAILED`.
**Экран:** Карточка связи (админ)
**Связи:** BR-LINK-006, BR-LINK-009

## 5. Уведомления (FR-NOTIF, серверная часть)

### FR-NOTIF-001 Очередь уведомлений
**Актор:** Система (worker)
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** событие, требующее уведомления (пропуск, напоминание, отвязка).
**Описание:** уведомления ставятся в очередь pg-boss в отдельном процессе `worker`. Повтор при сбое до 3 раз с экспоненциальной задержкой; после — dead-letter с requestId без PII. Очередь не хранится в памяти процесса (`CLAUDE.md` §5).
**Критерии приёмки:**
- Дано: событие пропуска, Когда worker недоступен, Тогда задача остаётся в очереди и выполняется после восстановления.
- Дано: доставка падает три раза, Когда исчерпаны повторы, Тогда задача в dead-letter, в логе нет адреса токена и текста.
**Ошибки:** 500 `INTERNAL` (внутреннее, клиенту не отдаётся).
**Экран:** нет (API)
**Связи:** BR-DATA-008, BR-SYNC-002

### FR-NOTIF-002 Push без персональных данных
**Актор:** Система (worker)
**Приоритет и этап:** Must, EPIC-4
**Предусловия:** уведомление отправляется через `PushProvider`.
**Описание:** текст push нейтральный и не содержит имени, здоровья, веса, плана, названия тренировки. Пример: «У вас новое обновление в приложении». Детали открываются в приложении после аутентификации.
**Критерии приёмки:**
- Дано: тренер изменил план, Когда push отправлен, Тогда текст не содержит названия упражнения, веса или имени тренера.
- Дано: в payload push попытка передать ID клиента, Когда формируется, Тогда отказ сборки payload (тест схемы).
**Ошибки:** нет (внутренняя проверка схемы; сбой отправки — FR-NOTIF-001).
**Экран:** нет (API)
**Связи:** BR-DATA-008, BR-SAFETY-002

### FR-NOTIF-003 Снятие напоминаний и будущих записей при отвязке
**Актор:** Система (worker)
**Приоритет и этап:** Must, EPIC-1
**Предусловия:** связь переведена в ended (FR-LINK-009, FR-ACCT-004).
**Описание:** при отвязке worker снимает запланированные напоминания и отменяет задачи pg-boss, связанные со связью. Будущие записи календаря удаляются тем же транзакционным шагом (не асинхронно). Снятие проверяется: задача, созданная до отвязки, не отправляется.
**Критерии приёмки:**
- Дано: связь с напоминанием на завтра, Когда связь завершена, Тогда задача напоминания отменена, при запуске не отправляется.
- Дано: задача уже выполняется в момент отвязки, Когда отправка завершилась, Тогда пользователь не видит данных связи, а текст push нейтрален (FR-NOTIF-002).
**Ошибки:** нет (внутренний процесс).
**Экран:** нет (API)
**Связи:** BR-LINK-009

### FR-NOTIF-004 Напоминания о пропусках и нейтральный тон [O5]
**Актор:** Система (worker), Клиент
**Приоритет и этап:** Should, EPIC-6
**Предусловия:** клиент разрешил push; есть запланированная тренировка; связь active; пауза не включена.
**Описание:** напоминание о тренировке в локальное время клиента (`DATE` в TZ клиента). Пропуск отмечается только после окончания дня клиента. Текст нейтральный, без стыда и стриков. Отказ в push не блокирует приложение: напоминания показываются в приложении.
**Критерии приёмки:**
- Дано: тренировка на сегодня, клиент в TZ `Europe/Berlin`, Когда наступило 07:00 местного времени, Тогда напоминание отправлено, текст нейтральный.
- Дано: клиент отказал в push, Когда наступает время напоминания, Тогда push не отправляется, приложение не показывает ошибку, список задач доступен на экране «Сегодня».
**Ошибки:** нет (напоминание не отправлено — без ошибки для клиента).
**Экран:** Сегодня (баннер «Включить уведомления»)
**Связи:** BR-DATE-002, BR-SAFETY-002, BR-SAFETY-004
