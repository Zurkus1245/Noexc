# 10. Функциональные требования: кабинет тренера

Дата: 2026-11-23. Статус: черновик v1 (для ревью владельца и разработки).
Основа: `00-validation.md` (решения O1–O8 приняты по рекомендациям, зависимые требования помечены `[O#]`), «NoExcuse — План MVP v1.1» (разделы 2.1, 3, 5), `noexcuse/CLAUDE.md` (разделы 5, 6, 9), исходное ТЗ (разделы 4.1, 5.1, 9, 10).
Охват: кабинет тренера (мобильный Expo-клиент, адаптив под планшет). Веб-кабинет тренера, оплата, рефералка, библиотека программ и навыки в документ не входят (План MVP, раздел 1).

## 0. Соглашения

### 0.1 Акторы
- **Тренер** — владелец аккаунта с ролью «тренер» (O1: одна роль на аккаунт).
- **Клиент** — пользователь, связанный с тренером активной или приостановленной связью. Упоминается только там, где его действие порождает ответ тренера.
- **Система** — бэкенд `apps/api` и `apps/worker` (отложенные задачи: дайджесты, удаление, экспорт).

### 0.2 Приоритеты и этапы
- **Must** — без этого бета-тест (этап 5) не стартует. **Should** — входит в MVP, но может сдвинуться в этап 6 без срыва беты. **Later** — вне MVP (в документе не используется).
- **EPIC-1** — связь тренер–клиент (этап 1). **EPIC-2** — план и календарь (этап 2). **EPIC-3** — факт и питание (этап 3). **EPIC-4** — готовность к бете: push, импорт CSV, экраны-сводки (этап 4). **EPIC-5** — закрытая бета: новых требований нет, есть метрики (раздел 1 плана). **EPIC-6** — остальное MVP, параллельно бете (этап 6).

### 0.3 Статусы клиента в списке
Статус вычисляется по приоритету сверху вниз (первый подошедший):
1. **на паузе** — связь в статусе `paused`.
2. **неактивен N дней** — нет ни одной отметки факта за последние `NOT_ACTIVE_DAYS` дней (по дате в TZ клиента).
3. **пропуск** — есть назначенная тренировка на прошедший день (TZ клиента), по которой нет отметки факта (BR-DATE-002).
4. **в плане** — есть назначение на сегодня или будущую дату.
5. **без плана** — назначений нет (допущение, см. раздел 10).

Цвета по плану: синий — действие, зелёный — в плане/выполнено, оранжевый — пропуск/внимание, красный — неактивен, серый — на паузе.

### 0.5 Коды ошибок (клиент ветвится по `code`, RFC 9457)
| Код | HTTP | Смысл |
|---|---|---|
| `VALIDATION_FAILED` | 422 | Ввод не прошёл схему `packages/contracts`; поле указано в `errors[]` |
| `RESOURCE_NOT_FOUND` | 404 | Ресурс не существует или не принадлежит тренеру (без раскрытия существования) |
| `INVITE_NOT_FOUND` | 404 | Инвайт не найден, истёк, отозван или уже использован (для клиента — единый ответ) |
| `INVITE_NOT_ACTIVE` | 409 | Операция над инвайтом в неподходящем статусе |
| `INVITE_RATE_LIMITED` | 429 | Превышен лимит создания инвайтов; есть `Retry-After` |
| `ONBOARDING_INCOMPLETE` | 403 | Не заполнены профиль, TZ или отметка квалификации |
| `ROLE_CONFLICT` | 409 | Аккаунт уже имеет другую роль (O1) |
| `LINK_NOT_ACTIVE` | 409 | Действие требует связи в статусе `active`/`paused`, связь в другом статусе |
| `LINK_NOT_PAUSED` | 409 | Снятие паузы для связи, которая не на паузе |
| `REQUEST_NOT_OPEN` | 409 | Запрос клиента уже обработан |
| `PLAN_VERSION_CONFLICT` | 409 | `baseVersion` меньше текущей версии плана |
| `CALENDAR_ENTRY_LOCKED` | 409 | Назначение выполнено или имеет факт; перенос запрещён |
| `DATE_IN_PAST` | 422 | Назначение или перенос на дату раньше сегодняшней по TZ клиента |
| `CALENDAR_RANGE_TOO_LARGE` | 422 | Диапазон `from/to` больше 31 дня |
| `EXERCISE_NOT_FOUND` | 404 | Упражнение удалено из справочника |
| `TEMPLATE_NOT_FOUND` | 404 | Шаблон удалён |
| `CONSENT_REQUIRED` | 403 | У клиента нет действующего согласия на категорию данных |
| `CONSENT_VERSION_OUTDATED` | 403 | Вышла новая версия согласия, клиент её не подтвердил |
| `MEASUREMENT_READ_ONLY` | 403 | Попытка тренера изменить замер клиента |
| `EXPORT_ALREADY_PENDING` | 409 | Заявка на экспорт уже в обработке |
| `REAUTH_REQUIRED` | 401 | Для удаления аккаунта нужна повторная аутентификация |
| `IMPORT_LIMIT_EXCEEDED` | 422 | CSV больше 200 строк или 1 МБ |
| `IMPORT_ROW_INVALID` | 422 | Строка CSV не прошла проверку (номер строки и причина в `errors[]`) |

| `MACRO_KCAL_MISMATCH` | 200, `warnings[]` | Предупреждение, не ошибка (NUT-003) |
| `OFFLINE` | — (клиент) | Нет сети; запись не отправлена |
| `NETWORK_TIMEOUT` | — (клиент) | Ответ не получен за 10 с |
| `SESSION_EXPIRED` | 401 | Сессия истекла; один refresh, затем выход |
| `SERVER_ERROR` | 5xx | Сбой сервера; показывается `requestId` для поддержки |

### 0.6 Бизнес-правила (BR-*)
| ID | Правило |
|---|---|
| BR-LINK-001 | На клиента одна связь в статусе `active` или `paused` (O2). |
| BR-LINK-002 | Пауза не закрывает доступ тренера к данным; она отключает напоминания клиенту и учёт пропусков (O3). |
| BR-LINK-003 | Отвязка закрывает доступ тренера в той же транзакции; будущие назначения снимаются. |
| BR-LINK-004 | История остаётся у клиента; после отвязки тренер не видит данных связи. |
| BR-LINK-005 | Одна роль на аккаунт (O1). Двойная роль — два аккаунта. |
| BR-CONSENT-001 | Согласие привязано к связи (тренер + клиент), а не к пользователю (устраняет K1). |
| BR-CONSENT-002 | Отзыв согласия закрывает доступ категории немедленно (сервер), экран обновляется за ≤30 с. |
| BR-CONSENT-003 | Раздельные согласия: тренировки и факт; замеры; питание (дневник). Согласие на связь и на данные — разные. |
| BR-CONSENT-004 | Новая версия согласия требует подтверждения клиента; до подтверждения доступ к затронутой категории закрыт (устраняет K5). |
| BR-INVITE-001 | Код инвайта не короче 128 бит, TTL 7 дней, одноразовый. |
| BR-INVITE-002 | Не более 5 созданных инвайтов на тренера за скользящий час. |
| BR-INVITE-003 | Любое негативное состояние инвайта для клиента — единый ответ `INVITE_NOT_FOUND` (404). Тренер видит только собственный статус инвайта. |
| BR-INVITE-004 | В БД хранится хэш кода; полный код тренер видит только в момент создания. |
| BR-SYNC-001 | Экраны тренера обновляют данные клиента за ≤30 с (`SYNC_REFRESH_SEC`). Закрытие доступа на сервере — немедленно. |
| BR-SYNC-002 | Версия плана: целое число, +1 на каждое сохранённое изменение; запрос несёт `baseVersion` и client-UUID операции (идемпотентность). |
| BR-DATE-001 | Дата тренировки — `YYYY-MM-DD` в TZ клиента. TZ хранится на аккаунте. |
| BR-DATE-002 | «Пропуск» формируется после окончания дня в TZ клиента. Неактивность — `NOT_ACTIVE_DAYS`. |
| BR-DATE-003 | Правка плана и перенос никогда не меняют прошедшие назначения и факт (K7; раздел 5 плана). |
| BR-GATE-001 | Единственный порог беты: клиент «активен», если отметил ≥1 тренировку за неделю. Метрика тренера — ≥3 активных клиентов у ≥3 из 5 тренеров на 4-й неделе (устраняет C3). |
| BR-NUT-001 | Ккал ниже `NUTRITION_MIN_KCAL` — предупреждение с подтверждением, не блокировка. Значение утверждает специалист. |
| BR-NUT-002 | Ккал считаются по БЖУ как 4·Б + 4·У + 9·Ж. Расхождение больше `MACRO_TOLERANCE_PCT` — предупреждение. |
| BR-SAFETY-001 | Экраны планов (тренировок и питания) показывают текст «Планы не являются медицинской рекомендацией»; при боли клиент прекращает занятие. |
| BR-SAFETY-002 | Квалификация тренера — самодекларация с подтверждением ответственности до верификации (вопрос владельца, план раздел 7.2). |
| BR-DATA-001 | Удаление аккаунта тренера: связи завершаются, данные удаляются в течение 30 дней каскадом (включая бэкапы по расписанию и push-токены). |
| BR-DATA-002 | Экспорт данных тренера готовится в течение 30 дней (GDPR). |
| BR-DATA-003 | Минимизация: push, логи, поиск и карточка не содержат лишних персональных данных; данные здоровья не покидают экраны с аутентификацией. |

## 1. FR-ACCT — Аккаунт тренера: онбординг, роль, удаление, общие требования

### FR-ACCT-201 Заполнение профиля тренера
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1 [O7]
- **Предусловия:** Тренер вошёл в аккаунт, роль не выбрана, онбординг не завершён.
- **Описание:** Тренер вводит имя (2–60 символов), выбирает язык интерфейса из словаря и страну из списка стран старта. Профиль сохраняется одним запросом. Код страны и язык фиксируются, чтобы при смене стартовой страны (O7) данные не терялись.
- **Критерии приёмки:**
  - Позитивный: Дано новый тренер на экране профиля, Когда он вводит имя из 2 символов, выбирает страну из списка и нажимает «Сохранить», Тогда профиль сохранён (ответ 200) и открыт экран часового пояса.
  - Негативный: Дано поле «Имя» пустое, Когда тренер нажимает «Сохранить», Тогда запрос не отправляется, у поля показано сообщение об ошибке, сервер получает 0 запросов.
- **Ошибки:** `VALIDATION_FAILED`, `OFFLINE`, `SESSION_EXPIRED`
- **Экран:** Онбординг: профиль
- **Связи:** BR-DATA-003, [O7]

### FR-ACCT-202 Часовой пояс тренера
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Сохранён профиль (FR-ACCT-201).
- **Описание:** Система предлагает часовой пояс устройства (IANA, например `Europe/Berlin`). Тренер подтверждает или выбирает другой. TZ хранится на аккаунте и используется для дайджестов (NOTIF-001) и отметки дня.
- **Критерии приёмки:**
  - Позитивный: Дано устройство в поясе `Europe/Berlin`, Когда тренер подтверждает предложенный пояс, Тогда на аккаунте сохранён `Europe/Berlin` и открыт экран квалификации.
  - Негативный: Дано в запросе передана строка, которой нет в списке IANA, Когда запрос приходит на сервер, Тогда ответ 422 `VALIDATION_FAILED` с полем `timezone`, значение на аккаунте не меняется.
- **Ошибки:** `VALIDATION_FAILED`, `OFFLINE`
- **Экран:** Онбординг: часовой пояс
- **Связи:** BR-DATE-001, BR-DATE-002

### FR-ACCT-203 Подтверждение квалификации тренера
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1 [O8]
- **Предусловия:** Сохранён часовой пояс (FR-ACCT-202).
- **Описание:** Тренер ставит отметку «Подтверждаю, что я тренер и несу ответственность за назначаемые планы» и, по желанию, указывает тип документа и год. Без отметки онбординг не завершается. Верификация документов в MVP не выполняется. Отметка сохраняется с датой и версией текста.
- **Критерии приёмки:**
  - Позитивный: Дано отметка не стоит, Когда тренер ставит её и нажимает «Завершить», Тогда онбординг завершён, на аккаунте записаны дата и версия текста подтверждения.
  - Негативный: Дано отметка не стоит, Когда тренер нажимает «Завершить», Тогда кнопка неактивна, онбординг не завершён, а попытка создать инвайт возвращает `ONBOARDING_INCOMPLETE`.
- **Ошибки:** `ONBOARDING_INCOMPLETE`, `VALIDATION_FAILED`, `OFFLINE`
- **Экран:** Онбординг: подтверждение квалификации
- **Связи:** BR-SAFETY-002, [O8]

### FR-ACCT-204 Одна роль на аккаунт
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1 [O1]
- **Предусловия:** Аккаунт имеет роль «тренер».
- **Описание:** Роль «тренер» назначается при онбординге и не меняется в приложении. Тренер, который сам тренируется, заводит второй аккаунт (другой адрес входа). Переключения ролей в настройках нет.
- **Критерии приёмки:**
  - Позитивный: Дано аккаунт тренера с завершённым онбордингом, Когда тренер открывает «Настройки аккаунта», Тогда раздела смены роли нет, а текст подсказывает завести второй аккаунт.
  - Негативный: Дано аккаунт тренера, Когда в обход интерфейса отправлен запрос на смену роли на «клиент», Тогда ответ 409 `ROLE_CONFLICT`, роль не меняется.
- **Ошибки:** `ROLE_CONFLICT`, `SESSION_EXPIRED`
- **Экран:** Настройки аккаунта
- **Связи:** BR-LINK-005, [O1]

### FR-ACCT-205 Гейт онбординга для действий с клиентами
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Аккаунт тренера с ролью «тренер».
- **Описание:** Создание инвайта, импорт клиентов и любые действия со связями доступны только после завершения онбординга (профиль, TZ, отметка квалификации). Незавершённый онбординг возобновляется с первого незаполненного шага.
- **Критерии приёмки:**
  - Позитивный: Дано онбординг завершён, Когда тренер открывает «Создать приглашение», Тогда открывается экран создания приглашения.
  - Негативный: Дано часовой пояс не задан, Когда тренер открывает «Создать приглашение», Тогда он переходит на экран часового пояса, а запрос создания возвращает 403 `ONBOARDING_INCOMPLETE`.
- **Ошибки:** `ONBOARDING_INCOMPLETE`, `SESSION_EXPIRED`
- **Экран:** Онбординг: шаг, на котором остановился тренер
- **Связи:** BR-SAFETY-002

### FR-ACCT-206 Удаление аккаунта тренера и судьба связей
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Тренер прошёл повторную аутентификацию в пределах 5 минут.
- **Описание:** Тренер подтверждает удаление текстом с названием действия. Система в одной транзакции: переводит все связи в `ended` (BR-LINK-003); отзывает все активные инвайты; снимает будущие назначения; у клиентов показывает статус «тренер удалил аккаунт» без данных тренера. Персональные данные тренера (профиль, шаблоны, заметки) удаляются в течение 30 дней каскадом (BR-DATA-001). Данные клиентов (история факта, замеры) остаются у клиентов и не удаляются при удалении тренера.
- **Критерии приёмки:**
  - Позитивный: Дано у тренера 3 активные связи и 2 активных инвайта, Когда тренер подтверждает удаление после повторного входа, Тогда все 3 связи в статусе `ended`, 2 инвайта `revoked`, будущие назначения удалены, аккаунт помечен к удалению с датой полного удаления не позднее 30 дней.
  - Негативный: Дано повторная аутентификация не пройдена или прошла более 5 минут назад, Когда тренер подтверждает удаление, Тогда ответ 401 `REAUTH_REQUIRED`, связи и инвайты не меняются.
- **Ошибки:** `REAUTH_REQUIRED`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Настройки аккаунта: удаление аккаунта
- **Связи:** BR-DATA-001, BR-LINK-003, BR-LINK-004

### FR-ACCT-207 Экспорт данных аккаунта тренера
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Аккаунт тренера; нет другой заявки на экспорт в статусе «в обработке».
- **Описание:** Тренер запрашивает выгрузку своих данных: профиль, список инвайтов, шаблоны и версии, настройки уведомлений. Данные клиентов в выгрузку тренера не входят (их получает клиент по собственному запросу). Файл JSON готовится worker-процессом, доступен для скачивания 7 дней, статус заявки видно в приложении.
- **Критерии приёмки:**
  - Позитивный: Дано у тренера есть 2 шаблона, Когда тренер запрашивает экспорт, Тогда создана заявка в статусе «в обработке», а через фоновую задачу в статусе «готово» появляется файл, доступный 7 дней.
  - Негативный: Дано заявка на экспорт уже в статусе «в обработке», Когда тренер запрашивает экспорт повторно, Тогда ответ 409 `EXPORT_ALREADY_PENDING`, новая заявка не создаётся.
- **Ошибки:** `EXPORT_ALREADY_PENDING`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Настройки аккаунта: экспорт данных
- **Связи:** BR-DATA-002

### FR-ACCT-208 Адаптив для планшета
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** Экраны кабинета тренера реализованы.
- **Описание:** Ширина от 768 px: двухколоночный режим: список клиентов слева, карточка или редактор справа, переход без перезагрузки экрана. Ширина до 767 px: одна колонка. Горизонтальная прокрутка страницы запрещена при ширине от 320 px. Тексты и кнопки не короче 44×44 pt. Требование WCAG 2.2 AA (контраст, фокус, не только цветом).
- **Критерии приёмки:**
  - Позитивный: Дано планшет в альбомной ориентации шириной 1024 px, Когда тренер открывает список клиентов и выбирает клиента, Тогда карточка открывается справа, список остаётся на месте.
  - Негативный: Дано ширина 320 px, Когда тренер открывает календарь клиента, Тогда страница не прокручивается по горизонтали, сетка недели заменяется списком дней.
- **Ошибки:** `—` (правило вёрстки; сетевые ошибки см. ACC-009)
- **Экран:** Все экраны кабинета тренера
- **Связи:** NFR (WCAG 2.2 AA), BR-SYNC-001

### FR-ACCT-209 Офлайн и ошибки на каждом экране
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Любой экран кабинета тренера с запросом к API.
- **Описание:** Каждый запрос завершается одним из состояний: загружено, пусто, `OFFLINE`, `NETWORK_TIMEOUT` (10 с), `SERVER_ERROR` (показывается `requestId`), `SESSION_EXPIRED` (один refresh, затем выход). Запись без ответа сервера показывается как «не отправлено» с кнопкой «Повторить». Надпись «сохранено» появляется только после ответа 200. Офлайн-очереди записи в MVP нет (CLAUDE.md, раздел 6).
- **Критерии приёмки:**
  - Позитивный: Дано сеть выключена, Когда тренер нажимает «Сохранить план», Тогда показано «Нет сети. Изменения не сохранены», кнопка «Повторить», статус «не отправлено».
  - Негативный: Дано сервер вернул 500 с `requestId`, Когда тренер сохраняет изменение, Тогда слово «сохранено» не показывается, на экране отображаются текст ошибки и `requestId`, запись в логах содержит `requestId` и не содержит персональных данных.
- **Ошибки:** `OFFLINE`, `NETWORK_TIMEOUT`, `SERVER_ERROR`, `SESSION_EXPIRED`
- **Экран:** Все экраны кабинета тренера
- **Связи:** BR-SYNC-001, BR-DATA-003

## 2. FR-LINK — Инвайт, связь, пауза, отвязка

### FR-LINK-201 Создание инвайта
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Пройден онбординг (FR-ACCT-205); в течение последнего часа создано меньше 5 инвайтов (FR-LINK-202).
- **Описание:** Система создаёт инвайт: код не короче 128 бит (base32, 26 символов), ссылка вида `https://<домен>/i/<код>`, статус `active`, срок 7 дней, одноразовый. Экран показывает код и ссылку, кнопка «Поделиться» открывает системный список. Полный код показывается только в момент создания (BR-INVITE-004); при утере тренер отзывает инвайт и создаёт новый.
- **Критерии приёмки:**
  - Позитивный: Дано онбординг завершён, Когда тренер нажимает «Создать приглашение», Тогда создан инвайт в статусе `active`, срок истекает ровно через 7 дней от создания, код и ссылка показаны, доступна кнопка «Поделиться».
  - Негативный: Дано нет сети, Когда тренер нажимает «Создать приглашение», Тогда инвайт не создан, экран показывает `OFFLINE`, код не отображается как готовый.
- **Ошибки:** `ONBOARDING_INCOMPLETE`, `INVITE_RATE_LIMITED`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Создание приглашения
- **Связи:** BR-INVITE-001, BR-INVITE-004

### FR-LINK-202 Лимит создания инвайтов
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Тренер создаёт инвайт.
- **Описание:** Не более 5 инвайтов на тренера за скользящий час. Шестой запрос отклоняется с `INVITE_RATE_LIMITED` и заголовком `Retry-After` (секунды до освобождения слота). Экран показывает сколько осталось и через сколько минут можно создать новый.
- **Критерии приёмки:**
  - Позитивный: Дано за последний час создано 4 инвайта, Когда тренер создаёт пятый, Тогда инвайт создан, экран показывает «Осталось 0 в этом часу».
  - Негативный: Дано за последний час создано 5 инвайтов, Когда тренер создаёт шестой, Тогда ответ 429 `INVITE_RATE_LIMITED`, инвайт не создан, экран показывает «Лимит 5 приглашений в час. Повторите через N мин».
- **Ошибки:** `INVITE_RATE_LIMITED`, `OFFLINE`
- **Экран:** Создание приглашения
- **Связи:** BR-INVITE-002

### FR-LINK-203 Список приглашений и их статусы
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Тренер прошёл онбординг.
- **Описание:** Список всех инвайтов тренера с датой создания, сроком и статусом: «активен», «принят» (после принятия показывается связь с клиентом), «истёк», «отозван». Из «истёк» и «отозван» есть действие «Создать новый». Список сортируется по дате создания, по 20 записей, дальше подгрузка по курсору.
- **Критерии приёмки:**
  - Позитивный: Дано инвайт создан 8 дней назад и не принят, Когда тренер открывает список, Тогда статус «истёк» и действие «Создать новый».
  - Негативный: Дано сервер недоступен, Когда тренер открывает список, Тогда показано `OFFLINE` и сообщение «Список может быть неактуален», статусы из кэша не выдаются за актуальные.
- **Ошибки:** `OFFLINE`, `NETWORK_TIMEOUT`, `SERVER_ERROR`
- **Экран:** Список приглашений
- **Связи:** BR-INVITE-001, BR-INVITE-003

### FR-LINK-204 Отзыв инвайта тренером
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Инвайт в статусе `active`.
- **Описание:** Тренер отзывает активный инвайт после подтверждения. Статус становится `revoked` немедленно; код перестаёт принимать. Отзыв не влияет на связи, созданные ранее по этому инвайту.
- **Критерии приёмки:**
  - Позитивный: Дано инвайт в статусе `active`, Когда тренер подтверждает «Отозвать», Тогда статус `revoked`, а клиент, открывший ссылку после этого, получает `INVITE_NOT_FOUND`.
  - Негативный: Дано инвайт уже принят клиентом, Когда тренер пытается отозвать его через список, Тогда действие недоступно, а прямой запрос возвращает 409 `INVITE_NOT_ACTIVE`, связь не меняется.
- **Ошибки:** `INVITE_NOT_ACTIVE`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Список приглашений
- **Связи:** BR-INVITE-003

### FR-LINK-205 Что видит тренер при неуспешном принятии инвайта
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Клиент пытается принять инвайт тренера, который не может быть принят (истёк, отозван, использован, клиент уже связан с другим тренером).
- **Описание:** Клиент получает единый ответ `INVITE_NOT_FOUND`. Тренер в списке видит только собственный статус инвайта: при неуспешной попытке статус не меняется (например, «активен»). Тренер не получает уведомления о причине и не узнаёт, есть ли у клиента другой тренер (BR-LINK-001, BR-INVITE-003).
- **Критерии приёмки:**
  - Позитивный: Дано инвайт истёк, Когда клиент вводит код, Тогда клиент получает «Приглашение не найдено», а у тренера статус «истёк», без признака попытки.
  - Негативный: Дано клиент уже связан с другим тренером, Когда он открывает инвайт этого тренера, Тогда инвайт остаётся в статусе «активен» у тренера, тренер не получает push и не видит причины.
- **Ошибки:** `INVITE_NOT_FOUND` (на стороне клиента), `OFFLINE` (на стороне тренера)
- **Экран:** Список приглашений
- **Связи:** BR-INVITE-003, BR-LINK-001

### FR-LINK-206 Пауза связи тренером
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1 [O3]
- **Предусловия:** Связь в статусе `active`.
- **Описание:** Тренер ставит связь на паузу с причиной из списка («отпуск», «болезнь», «другое») и необязательной датой окончания. На время паузы: данные остаются доступны тренеру (BR-LINK-002); напоминания клиенту отключаются; пропуски не учитываются в статусах и дайджесте; назначения сохраняются. Клиент видит статус паузы.
- **Критерии приёмки:**
  - Позитивный: Дано связь `active`, Когда тренер ставит паузу с причиной «болезнь» и датой окончания через 5 дней, Тогда статус клиента «на паузе», пропуски в этот период не формируются, карточка клиента доступна тренеру.
  - Негативный: Дано связь уже на паузе или завершена, Когда тренер нажимает «Пауза», Тогда ответ 409 `LINK_NOT_ACTIVE`, статус не меняется.
- **Ошибки:** `LINK_NOT_ACTIVE`, `VALIDATION_FAILED` (дата окончания раньше сегодня), `OFFLINE`
- **Экран:** Карточка клиента: связь и пауза
- **Связи:** BR-LINK-002, BR-DATE-002, [O3]

### FR-LINK-207 Ответ тренера на запрос клиента о паузе
- **Актор:** Тренер (ответ), Клиент (запрос)
- **Приоритет / этап:** Must / EPIC-1 [O3]
- **Предусловия:** Клиент отправил запрос паузы (даты «с–по», причина, до 280 символов).
- **Описание:** Запрос появляется на экране «Запросы клиентов» с датами, причиной и счётчиком ожидания. Тренер подтверждает или отклоняет запрос; отказ сопровождается необязательным комментарием до 280 символов. Подтверждение создаёт паузу по FR-LINK-206 на указанные даты. Непроцессированные запросы остаются открытыми и попадают в «Реакция сегодня» (CLIENTS-003).
- **Критерии приёмки:**
  - Позитивный: Дано открыт запрос паузы с 10.12 по 14.12, Когда тренер подтверждает его, Тогда связь на паузе с 10.12 по 14.12, запрос в статусе «подтверждён», пропуски за эти даты не учитываются.
  - Негативный: Дано запрос уже подтверждён на другом устройстве, Когда тренер нажимает «Подтвердить» на устаревшем экране, Тогда ответ 409 `REQUEST_NOT_OPEN`, экран показывает актуальный статус запроса.
- **Ошибки:** `REQUEST_NOT_OPEN`, `LINK_NOT_ACTIVE`, `VALIDATION_FAILED` (дата «с» позже «по»), `OFFLINE`
- **Экран:** Запросы клиентов
- **Связи:** BR-LINK-002, BR-SYNC-001, [O3]

### FR-LINK-208 Отвязка клиента тренером
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Связь в статусе `active` или `paused`.
- **Описание:** Тренер подтверждает отвязку, после чего система в одной транзакции: переводит связь в `ended`; закрывает доступ тренера ко всем данным клиента; удаляет будущие назначения календаря (K8); снимает напоминания клиенту; отзывает связанные запросы в статусе «закрыт». Клиенту отправляется push без персональных данных о завершении связи. Тренер сохраняет только факт и дату завершения связи. Клиент в списке тренера переходит в «Архив».
- **Критерии приёмки:**
  - Позитивный: Дано у связи 2 будущих назначения, Когда тренер подтверждает отвязку, Тогда связь `ended`, будущие назначения удалены, все запросы API по клиенту возвращают 404 `RESOURCE_NOT_FOUND`, клиент переходит в «Архив», экран обновляется за ≤30 с.
  - Негативный: Дано связь уже `ended`, Когда тренер повторно подтверждает отвязку, Тогда ответ 409 `LINK_NOT_ACTIVE`, данные не меняются.
- **Ошибки:** `LINK_NOT_ACTIVE`, `VALIDATION_FAILED` (нет подтверждения), `OFFLINE`, `SERVER_ERROR`
- **Экран:** Карточка клиента: завершение связи
- **Связи:** BR-LINK-003, BR-LINK-004, BR-DATE-003

### FR-LINK-209 Повторная связь после отвязки
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Связь с клиентом завершена (FR-LINK-208).
- **Описание:** Новый инвайт создаёт новую связь с новым идентификатором. Согласия по старой связи не переносятся (BR-CONSENT-001); клиент подтверждает их заново. Старые данные тренеру не показываются.
- **Критерии приёмки:**
  - Позитивный: Дано связь с клиентом завершена, Когда тренер создаёт новый инвайт, и клиент его принимает, Тогда создана новая связь, согласия запрошены заново, в карточке показана только новая связь.
  - Негативный: Дано связь завершена 9 дней назад, Когда тренер открывает карточку прежнего клиента по старой ссылке, Тогда ответ 404 `RESOURCE_NOT_FOUND`, данные не загружаются.
- **Ошибки:** `RESOURCE_NOT_FOUND`, `INVITE_RATE_LIMITED`, `OFFLINE`
- **Экран:** Архив клиентов; Создание приглашения
- **Связи:** BR-LINK-004, BR-CONSENT-001

## 3. FR-CLIENTS — Клиенты: список, реакция, карточка, согласия, импорт

### FR-CLIENTS-001 Список клиентов со статусами
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Есть хотя бы одна связь в статусах `active` или `paused`.
- **Описание:** Список активных клиентов с именем, статусом по правилам раздела 0.3 и цветом статуса. Порядок: «пропуск» и «неактивен» сверху, затем «в плане», «на паузе», «без плана». Список загружается по 20, подгрузка по курсору.
- **Критерии приёмки:**
  - Позитивный: Дано клиент А назначен на сегодня, клиент Б пропустил вчерашнюю тренировку, клиент В не отмечал факт 8 дней, Когда тренер открывает список, Тогда А показан как «в плане» (зелёный), Б как «пропуск» (оранжевый), В как «неактивен 8 дн.» (красный), порядок В, Б, А.
  - Негативный: Дано сервер не ответил за 10 с, Когда тренер открывает список, Тогда показано `NETWORK_TIMEOUT` с кнопкой «Повторить», статусы не отображаются.
- **Ошибки:** `NETWORK_TIMEOUT`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Список клиентов
- **Связи:** BR-DATE-002, BR-SYNC-001

### FR-CLIENTS-002 Пустой список клиентов
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Онбординг завершён.
- **Описание:** Если активных клиентов нет, список заменяется состоянием «Клиентов пока нет» с кнопками «Создать приглашение» и «Импорт из CSV». Если клиенты есть, но выбранный фильтр пуст, показывается «Нет клиентов с этим статусом» без кнопки создания.
- **Критерии приёмки:**
  - Позитивный: Дано у тренера 0 связей, Когда он открывает список, Тогда показано состояние «Клиентов пока нет» с кнопкой «Создать приглашение».
  - Негативный: Дано у тренера 3 клиента, все «в плане», Когда он выбирает фильтр «на паузе», Тогда показано «Нет клиентов с этим статусом», а не пустое состояние без клиентов.
- **Ошибки:** `OFFLINE`
- **Экран:** Список клиентов
- **Связи:** BR-INVITE-001

### FR-CLIENTS-003 Экран «Кому нужна реакция сегодня» [O5]
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-4 [O5]
- **Предусловия:** Есть клиенты со статусом «пропуск» или «неактивен», либо открытые запросы клиентов.
- **Описание:** Отдельный экран и счётчик в навигации: клиенты, которым нужна реакция сегодня. Порядок: открытые запросы паузы и переноса, затем «неактивен», затем «пропуск». У каждой строки причина и кнопка перехода в карточку. Пауза клиентов с «на паузе» сюда не попадает. Пустой экран: «Сегодня реагировать не на кого».
- **Критерии приёмки:**
  - Позитивный: Дано у клиента открыт запрос паузы и вчера пропуск, Когда тренер открывает экран, Тогда первым стоит запрос, вторым пропуск, счётчик показывает 2.
  - Негативный: Дано сети нет, Когда тренер открывает экран, Тогда показано `OFFLINE`, счётчик не обновляется и не показывает устаревшее значение как актуальное.
- **Ошибки:** `OFFLINE`, `NETWORK_TIMEOUT`
- **Экран:** Реакция сегодня
- **Связи:** BR-DATE-002, BR-SYNC-001, [O5]

### FR-CLIENTS-004 Карточка клиента
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Связь клиента с тренером в статусе `active` или `paused`.
- **Описание:** Карточка содержит: имя, статус связи, дату начала связи, цель клиента, блоки «Согласия» (FR-CLIENTS-006), «План тренировок», «План питания», «Факт за неделю» (WORK-004), «Замеры» (PROG-001), действия «Пауза» и «Завершить связь». Email и телефон клиента в карточке не показываются.
- **Критерии приёмки:**
  - Позитивный: Дано связь `active`, согласия на тренировки и замеры есть, Когда тренер открывает карточку, Тогда видны блоки «План тренировок», «Факт за неделю», «Замеры», а email и телефон не показаны.
  - Негативный: Дано клиент не связан с тренером, Когда тренер открывает карточку по прямой ссылке с идентификатором клиента, Тогда ответ 404 `RESOURCE_NOT_FOUND`, экран «Клиент не найден», данные не загружаются.
- **Ошибки:** `RESOURCE_NOT_FOUND`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Карточка клиента
- **Связи:** BR-LINK-001, BR-DATA-003, BR-CONSENT-001

### FR-CLIENTS-005 Импорт клиентов из CSV [O5]
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-4 [O5]
- **Предусловия:** Онбординг завершён; файл UTF-8, до 200 строк и 1 МБ; колонки «имя» и «email» или «телефон».
- **Описание:** Импорт создаёт инвайты, а не связи: каждый клиент должен принять приглашение. Валидные строки создают инвайты в статусе `active`; ошибочные возвращаются списком с номером строки и причиной. Контакты клиента хранятся только в инвайте и удаляются при его закрытии или истечении срока. Импорт ограничен одним запуском в сутки (раздел 10, решение по лимиту 5/час).
- **Критерии приёмки:**
  - Позитивный: Дано CSV содержит 10 валидных строк, Когда тренер загружает файл, Тогда создано 10 инвайтов в статусе `active`, отчёт «10 создано, 0 ошибок».
  - Негативный: Дано CSV содержит 201 строку, Когда тренер загружает файл, Тогда ответ 422 `IMPORT_LIMIT_EXCEEDED`, ни одна строка не импортирована.
- **Ошибки:** `IMPORT_LIMIT_EXCEEDED`, `IMPORT_ROW_INVALID`, `VALIDATION_FAILED`, `OFFLINE`
- **Экран:** Импорт клиентов
- **Связи:** BR-INVITE-001, BR-INVITE-002, BR-DATA-003, [O5]

### FR-CLIENTS-006 Видимость согласий в карточке
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Связь активна.
- **Описание:** Блок «Согласия» показывает для каждой категории (тренировки и факт; замеры; питание) один из статусов: «разрешено», «не разрешено клиентом», «ожидает подтверждения клиента» (CLIENTS-008). Для «не разрешено» данные категории не запрашиваются, блок показывает текст без деталей.
- **Критерии приёмки:**
  - Позитивный: Дано клиент разрешил тренировки и не разрешил питание, Когда тренер открывает карточку, Тогда тренировки доступны, питание показано как «не разрешено клиентом».
  - Негативный: Дано согласие на замеры отозвано, Когда тренер открывает блок замеров, Тогда ответ 403 `CONSENT_REQUIRED`, блок показывает «Клиент не разрешил доступ к замерам», данные не загружаются.
- **Ошибки:** `CONSENT_REQUIRED`, `OFFLINE`
- **Экран:** Карточка клиента: согласия
- **Связи:** BR-CONSENT-001, BR-CONSENT-003

### FR-CLIENTS-007 Отзыв согласия клиентом
- **Актор:** Клиент (действие), Тренер (наблюдение)
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Согласие на категорию разрешено и связь активна.
- **Описание:** Когда клиент отзывает согласие на категорию, доступ тренера к ней закрывается на сервере в той же транзакции. Экран тренера обновляется за ≤30 с. Тренер не получает уведомления о причине. Клиент, у которого отозвано согласие на тренировки, исключается из «Реакция сегодня» и не формирует пропусков.
- **Критерии приёмки:**
  - Позитивный: Дано тренер открыл карточку при активном согласии на замеры, Когда клиент отзывает это согласие, Тогда через ≤30 с блок замеров показывает «не разрешено клиентом», API по замерам возвращает 403 `CONSENT_REQUIRED`.
  - Негативный: Дано клиент отозвал согласие на тренировки, Когда тренер открывает «Реакция сегодня», Тогда клиент не попадает в список, пропуск по нему не формируется.
- **Ошибки:** `CONSENT_REQUIRED`, `OFFLINE`
- **Экран:** Карточка клиента: согласия; Реакция сегодня
- **Связи:** BR-CONSENT-002, BR-SYNC-001

### FR-CLIENTS-008 Версия согласия, ожидающая подтверждения клиента
- **Актор:** Клиент (подтверждение), Тренер (наблюдение)
- **Приоритет / этап:** Must / EPIC-1
- **Предусловия:** Опубликована новая версия текста согласия на категорию.
- **Описание:** До подтверждения клиентом новой версии доступ тренера к затронутой категории закрыт (K5). Тренер видит статус «ожидает подтверждения клиента» без причины. Доступ восстанавливается после подтверждения без участия тренера.
- **Критерии приёмки:**
  - Позитивный: Дано вышла версия v2 согласия на тренировки и клиент её не подтвердил, Когда тренер открывает карточку, Тогда статус «ожидает подтверждения клиента», API тренировок возвращает 403 `CONSENT_VERSION_OUTDATED`.
  - Негативный: Дано версия согласия не менялась, Когда тренер открывает карточку, Тогда статуса «ожидает подтверждения» нет, доступ к тренировкам открыт.
- **Ошибки:** `CONSENT_VERSION_OUTDATED`, `OFFLINE`
- **Экран:** Карточка клиента: согласия
- **Связи:** BR-CONSENT-004

### FR-CLIENTS-009 Поиск по имени клиента
- **Актор:** Тренер
- **Приоритет / этап:** Should / EPIC-6
- **Предусловия:** Список клиентов загружен.
- **Описание:** Поиск по имени (от 2 символов), совпадение без учёта регистра и ё/е. Поиск выполняется на клиенте по загруженным записям, без отправки введённого текста на сервер. Фильтр по статусу комбинируется с поиском.
- **Критерии приёмки:**
  - Позитивный: Дано в списке 300 клиентов, Когда тренер вводит «ма», Тогда список сужается до совпадений за ≤300 мс.
  - Негативный: Дано введён 1 символ, Когда тренер вводит его, Тогда поиск не выполняется, список не меняется.
- **Ошибки:** `OFFLINE` (только при подгрузке недостающих страниц)
- **Экран:** Список клиентов
- **Связи:** BR-DATA-003

## 4. FR-PLAN — Блоки, тренировки, упражнения, версии, шаблоны

### FR-PLAN-001 Создание блока плана
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** Открыт план клиента или шаблон.
- **Описание:** Блок имеет название (1–60 символов), длительность 1–12 недель и порядковый номер. Блоки нумеруются подряд без пропусков. Создание увеличивает версию плана на 1 (BR-SYNC-002).
- **Критерии приёмки:**
  - Позитивный: Дано план клиента в версии 3, Когда тренер создаёт блок «Неделя 1–4» на 4 недели, Тогда блок сохранён, версия плана становится 4.
  - Негативный: Дано длительность 0, Когда тренер сохраняет блок, Тогда ответ 422 `VALIDATION_FAILED` с полем «Длительность», версия не меняется.
- **Ошибки:** `VALIDATION_FAILED`, `PLAN_VERSION_CONFLICT`, `OFFLINE`
- **Экран:** Редактор плана
- **Связи:** BR-SYNC-002

### FR-PLAN-002 Создание тренировки в блоке
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** Существует блок.
- **Описание:** Тренировка имеет название (1–80 символов) и номер дня цикла (1–7) внутри блока. Тренировка создаётся с пустым списком упражнений; упражнения добавляются по PLAN-003.
- **Критерии приёмки:**
  - Позитивный: Дано блок существует в версии 5, Когда тренер создаёт тренировку «День А» с номером дня 1, Тогда тренировка добавлена, версия становится 6.
  - Негативный: Дано блок удалён другим тренером или на другом устройстве, Когда тренер сохраняет тренировку, Тогда ответ 404 `RESOURCE_NOT_FOUND`, экран обновляет структуру плана.
- **Ошибки:** `RESOURCE_NOT_FOUND`, `PLAN_VERSION_CONFLICT`, `VALIDATION_FAILED`, `OFFLINE`
- **Экран:** Редактор тренировки
- **Связи:** BR-SYNC-002

### FR-PLAN-003 Добавление упражнения из справочника
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** Открыта тренировка.
- **Описание:** Тренер ищет упражнение в справочнике по названию и группе мышц и добавляет его в тренировку с порядковым номером. В MVP справочник наполняется заранее (seed и правки через админку). Собственные упражнения тренера вне MVP.
- **Критерии приёмки:**
  - Позитивный: Дано в справочнике есть «Приседания со штангой», Когда тренер ищет «присед» и добавляет упражнение, Тогда упражнение появляется в тренировке с порядковым номером на 1 больше последнего.
  - Негативный: Дано упражнение удалено из справочника после открытия экрана выбора, Когда тренер добавляет его, Тогда ответ 404 `EXERCISE_NOT_FOUND`, тренировка не меняется.
- **Ошибки:** `EXERCISE_NOT_FOUND`, `PLAN_VERSION_CONFLICT`, `OFFLINE`
- **Экран:** Выбор упражнения
- **Связи:** BR-SYNC-002

### FR-PLAN-004 Подходы: повторы, вес, отдых
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** Упражнение добавлено в тренировку.
- **Описание:** Для упражнения задаётся список подходов (1–20). У подхода обязательно число повторов (1–100); вес (0–500 кг, шаг 0,5) и отдых (0–600 с, шаг 5) необязательны, чтобы поддержать упражнения с собственным весом. Валидация одной схемой в `packages/contracts` на клиенте и сервере.
- **Критерии приёмки:**
  - Позитивный: Дано упражнение без подходов, Когда тренер задаёт 4 подхода по 8 повторов, 60 кг, отдых 120 с, Тогда подходы сохранены, на экране 4 строки.
  - Негативный: Дано в подходе 0 повторов или вес 501 кг, Когда тренер сохраняет, Тогда запрос не отправляется, поле подсвечено сообщением об ошибке; при обходе клиента сервер возвращает 422 `VALIDATION_FAILED`.
- **Ошибки:** `VALIDATION_FAILED`, `PLAN_VERSION_CONFLICT`, `OFFLINE`
- **Экран:** Редактор упражнения
- **Связи:** BR-SYNC-002

### FR-PLAN-005 Версия плана и идемпотентность сохранения
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** План клиента или шаблон открыт в версии N.
- **Описание:** Каждое сохранённое изменение структуры плана создаёт версию N+1. Запрос содержит `baseVersion` (версия, на которой выполнена правка) и client-UUID операции. Сервер применяет изменение атомарно. Повторная отправка с тем же UUID не создаёт второй версии и возвращает результат первой.
- **Критерии приёмки:**
  - Позитивный: Дано план в версии 5, Когда тренер сохраняет изменение с `baseVersion` 5 и новым UUID, Тогда ответ содержит версию 6, в истории версий одна запись на эту операцию.
  - Негативный: Дано первая отправка с UUID X прошла, но ответ потерян, Когда приложение повторяет запрос с UUID X, Тогда сервер возвращает версию 6 без повторного применения, версия плана остаётся 6.
- **Ошибки:** `PLAN_VERSION_CONFLICT`, `VALIDATION_FAILED`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Редактор плана
- **Связи:** BR-SYNC-002

### FR-PLAN-006 Конфликт версий плана
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** Тренер открыл план в версии 5 и редактирует его.
- **Описание:** Если `baseVersion` меньше текущей версии, сервер отклоняет операцию с `PLAN_VERSION_CONFLICT` и не применяет её. Экран показывает актуальную версию плана, сообщение «План изменили в другой сессии» и кнопку «Обновить». Правка, которую тренер делал, не теряется: ему показывается, что именно было в его черновике, и предлагается применить её повторно.
- **Критерии приёмки:**
  - Позитивный: Дано тренер A открыл план v5, тренер B сохранил v6, Когда A сохраняет изменение с `baseVersion` 5, Тогда 409 `PLAN_VERSION_CONFLICT`, A видит v6 и кнопку «Обновить», черновик A сохранён на экране.
  - Негативный: Дано A обновил план до v6 и сохраняет с `baseVersion` 6, Когда запрос отправлен, Тогда изменение сохранено как v7, конфликта нет.
- **Ошибки:** `PLAN_VERSION_CONFLICT`, `OFFLINE`
- **Экран:** Редактор плана: конфликт версий
- **Связи:** BR-SYNC-002

### FR-PLAN-007 Сохранение плана как шаблона [Should]
- **Актор:** Тренер
- **Приоритет / этап:** Should / EPIC-6
- **Предусловия:** План клиента существует.
- **Описание:** Тренер сохраняет план клиента как шаблон: блоки, тренировки, упражнения и подходы копируются. Шаблон получает собственную версию 1. Дальнейшие правки шаблона и плана клиента не влияют друг на друга, пока тренер не выполнит PLAN-009.
- **Критерии приёмки:**
  - Позитивный: Дано план клиента в версии 9, Когда тренер сохраняет его как шаблон «Сила 8 недель», Тогда создан шаблон версии 1 с тем же содержимым.
  - Негативный: Дано название шаблона пустое или длиннее 80 символов, Когда тренер сохраняет, Тогда ответ 422 `VALIDATION_FAILED`, шаблон не создан.
- **Ошибки:** `VALIDATION_FAILED`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Редактор плана: сохранение шаблона
- **Связи:** BR-SYNC-002

### FR-PLAN-008 Назначение шаблона клиенту копией [Should]
- **Актор:** Тренер
- **Приоритет / этап:** Should / EPIC-6
- **Предусловия:** Шаблон существует; клиент в статусе `active` или `paused`.
- **Описание:** Тренер выбирает шаблон и дату старта. Система копирует шаблон в план клиента (новая версия плана клиента, источник: шаблон и его версия) и создаёт назначения по датам в TZ клиента. Изменения шаблона после назначения клиента не затрагивают.
- **Критерии приёмки:**
  - Позитивный: Дано шаблон в версии 3, Когда тренер назначает его клиенту со стартом 01.12.2026, Тогда в плане клиента появилась копия версии 3, назначения начинаются с 01.12, шаблон не изменён.
  - Негативный: Дано шаблон удалён после открытия экрана, Когда тренер подтверждает назначение, Тогда ответ 404 `TEMPLATE_NOT_FOUND`, план клиента не меняется.
- **Ошибки:** `TEMPLATE_NOT_FOUND`, `PLAN_VERSION_CONFLICT`, `OFFLINE`
- **Экран:** Назначение шаблона
- **Связи:** BR-SYNC-002, BR-DATE-001

### FR-PLAN-009 Обновление копии у клиента как явное действие [Should]
- **Актор:** Тренер
- **Приоритет / этап:** Should / EPIC-6
- **Предусловия:** У клиента назначен шаблон; версия шаблона выше версии, на которой назначено.
- **Описание:** Правка шаблона не меняет планы клиентов. В карточке клиента и в шаблоне показывается «версия шаблона N, у клиента M». Кнопка «Обновить у клиента» открывает диалог с перечнем изменений и подтверждением. После подтверждения создаётся новая версия плана клиента. Прошедшие назначения не меняются (BR-DATE-003).
- **Критерии приёмки:**
  - Позитивный: Дано шаблон в версии 4, у клиента копия версии 3, Когда тренер подтверждает «Обновить у клиента», Тогда план клиента получает содержимое версии 4 новой версией, прошедшие назначения сохраняют прежний состав.
  - Негативный: Дано диалог открыт, Когда тренер закрывает его без подтверждения, Тогда версия плана клиента не меняется, клиент видит прежний план.
- **Ошибки:** `PLAN_VERSION_CONFLICT`, `TEMPLATE_NOT_FOUND`, `OFFLINE`
- **Экран:** Диалог обновления копии у клиента
- **Связи:** BR-SYNC-002, BR-DATE-003

### FR-PLAN-010 Статус «клиент ещё не видел обновление»
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** Тренер сохранил версию плана клиента.
- **Описание:** Сервер хранит последнюю версию плана, которую клиент открыл (`seenVersion`). Если версия тренера больше `seenVersion`, карточка клиента показывает «Клиент ещё не видел обновление (версия N)» и дату последнего сохранения. Статус снимается, когда клиент открывает план этой версии. Статус появляется у тренера и в списке клиентов.
- **Критерии приёмки:**
  - Позитивный: Дано тренер сохранил версию 7, клиент открывал версию 6, Когда тренер открывает карточку клиента, Тогда показано «Клиент ещё не видел обновление (версия 7)».
  - Негативный: Дано клиент открыл версию 7, Когда тренер обновляет карточку, Тогда статус «ещё не видел» не показан.
- **Ошибки:** `OFFLINE`, `SERVER_ERROR`
- **Экран:** Карточка клиента; Список клиентов
- **Связи:** BR-SYNC-001, BR-SYNC-002

## 5. FR-CAL — Календарь: назначение, перенос, пустое состояние, копирование

### FR-CAL-001 Назначение тренировки на дату
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** План клиента содержит тренировку.
- **Описание:** Тренер назначает тренировку на дату в TZ клиента. Назначение фиксирует версию плана, на которой создано. Не больше `WORKOUTS_PER_DAY_MAX` тренировок на день. Клиент видит назначение после обновления экрана (BR-SYNC-001).
- **Критерии приёмки:**
  - Позитивный: Дано план в версии 5 и дата через 3 дня по TZ клиента, Когда тренер назначает «День А» на эту дату, Тогда назначение создано с версией 5, клиент видит его после обновления экрана.
  - Негативный: Дано дата вчера по TZ клиента, Когда тренер назначает тренировку, Тогда ответ 422 `DATE_IN_PAST`, календарь не меняется.
- **Ошибки:** `DATE_IN_PAST`, `RESOURCE_NOT_FOUND`, `PLAN_VERSION_CONFLICT`, `OFFLINE`
- **Экран:** Назначение на дату
- **Связи:** BR-DATE-001, BR-DATE-003

### FR-CAL-002 Перенос тренировки тренером
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** Назначение на будущую дату без факта.
- **Описание:** Тренер переносит назначение на другую будущую дату. Старая запись получает статус «перенесено с <дата>» и остаётся в истории; создаётся новая запись. Перенос не стирает и не переносит факт, так как его нет (факт запрещено перенести, см. негатив).
- **Критерии приёмки:**
  - Позитивный: Дано назначение на 10.12 без факта, Когда тренер переносит его на 12.12, Тогда 10.12 показано как «перенесено на 12.12», 12.12 содержит тренировку.
  - Негативный: Дано клиент отметил факт по назначению на 10.12, Когда тренер пытается перенести его, Тогда ответ 409 `CALENDAR_ENTRY_LOCKED`, назначение не меняется.
- **Ошибки:** `CALENDAR_ENTRY_LOCKED`, `DATE_IN_PAST`, `VALIDATION_FAILED`, `OFFLINE`
- **Экран:** Календарь клиента
- **Связи:** BR-DATE-003

### FR-CAL-003 Пустой календарь
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** Открыт календарь клиента.
- **Описание:** Если на выбранную неделю назначений нет, календарь показывает «Нет тренировок на эту неделю» с кнопками «Назначить тренировку» и «Копировать неделю» (CAL-006). Если плана нет вообще, показывается «У клиента ещё нет плана» с кнопкой «Создать план». Сетка пустых дней без подписи не выводится.
- **Критерии приёмки:**
  - Позитивный: Дано у клиента есть план, но нет назначений на неделю, Когда тренер открывает календарь, Тогда показано «Нет тренировок на эту неделю» и кнопка «Назначить тренировку».
  - Негативный: Дано календарь не загрузился из-за сети, Когда тренер открывает его, Тогда показано `OFFLINE` с кнопкой «Повторить», состояние «пусто» не выводится, так как оно вводит в заблуждение.
- **Ошибки:** `OFFLINE`, `NETWORK_TIMEOUT`
- **Экран:** Календарь клиента
- **Связи:** BR-SYNC-001

### FR-CAL-004 Просмотр календаря за диапазон дат
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** Открыт календарь клиента.
- **Описание:** Запрос календаря задаёт диапазон `from`/`to` в формате `YYYY-MM-DD` в TZ клиента, максимум `CALENDAR_RANGE_MAX_DAYS` (31) дней. Ответ содержит назначения с версией плана, статусом дня (WORK-003) и признаком «перенесено».
- **Критерии приёмки:**
  - Позитивный: Дано диапазон 2026-12-01..2026-12-07, Когда тренер открывает неделю, Тогда возвращены назначения за 7 дней, каждое с версией плана и статусом дня.
  - Негативный: Дано диапазон 60 дней, Когда тренер открывает календарь, Тогда ответ 422 `CALENDAR_RANGE_TOO_LARGE`, данные не возвращаются.
- **Ошибки:** `CALENDAR_RANGE_TOO_LARGE`, `VALIDATION_FAILED`, `OFFLINE`
- **Экран:** Календарь клиента
- **Связи:** BR-DATE-001

### FR-CAL-005 Прошедшие назначения неизменяемы
- **Актор:** Тренер (правка), Система (отображение)
- **Приоритет / этап:** Must / EPIC-2
- **Предусловия:** Назначение на дату, которая уже прошла по TZ клиента.
- **Описание:** Правка плана создаёт новую версию только для будущих назначений. Прошедшее назначение показывает состав той версии, на которой оно было выполнено или назначено. Назначить правку задним числом нельзя (DATE_IN_PAST). Это устраняет K7: прошлые дни не меняются задним числом.
- **Критерии приёмки:**
  - Позитивный: Дано назначение на 05.12 создано на версии 5, Когда тренер правит тренировку (версия 6) и затем открывает 05.12, которое уже прошло, Тогда 05.12 показывает состав версии 5.
  - Негативный: Дано 05.12 уже прошло, Когда тренер пытается назначить на эту дату тренировку по новой версии, Тогда ответ 422 `DATE_IN_PAST`, назначение не создано.
- **Ошибки:** `DATE_IN_PAST`, `PLAN_VERSION_CONFLICT`
- **Экран:** Календарь клиента
- **Связи:** BR-DATE-003, BR-SYNC-002

### FR-CAL-006 Копирование недели [Should]
- **Актор:** Тренер
- **Приоритет / этап:** Should / EPIC-6
- **Предусловия:** На исходной неделе есть назначения.
- **Описание:** Тренер копирует назначения одной недели на N следующих недель (N от 1 до `COPY_WEEK_MAX_WEEKS`, 12). Дни, на которые уже есть назначения, пропускаются, в отчёте показывается число пропущенных. Прошедшие даты не заполняются. Перезаписи по умолчанию нет.
- **Критерии приёмки:**
  - Позитивный: Дано на неделю назначены 4 тренировки, целевые 3 недели пусты, Когда тренер копирует неделю на 3 недели, Тогда создано 12 назначений, отчёт «создано 12, пропущено 0».
  - Негативный: Дано N = 13, Когда тренер запускает копирование, Тогда ответ 422 `VALIDATION_FAILED` с полем «Количество недель», назначения не созданы.
- **Ошибки:** `VALIDATION_FAILED`, `DATE_IN_PAST`, `PLAN_VERSION_CONFLICT`, `OFFLINE`
- **Экран:** Копирование недели
- **Связи:** BR-DATE-001, BR-SYNC-002

### FR-CAL-007 Запрос клиента на перенос: ответ тренера [Should]
- **Актор:** Клиент (запрос), Тренер (ответ)
- **Приоритет / этап:** Should / EPIC-6
- **Предусловия:** Клиент отправил запрос переноса назначения.
- **Описание:** Клиент запрашивает перенос в пределах окна, которое задал тренер (по умолчанию 3 дня, не более 2 переносов в неделю). Запрос появляется в «Запросах клиентов». Тренер подтверждает (тогда выполняется CAL-002) или отклоняет. Запрос, не попавший в окно, в очередь тренера не попадает.
- **Критерии приёмки:**
  - Позитивный: Дано запрос переноса с 10.12 на 12.12 внутри окна 3 дня и лимита, Когда тренер подтверждает, Тогда назначение перенесено по CAL-002, запрос в статусе «подтверждён».
  - Негативный: Дано запрос уже подтверждён, Когда тренер нажимает «Подтвердить» на устаревшем экране, Тогда ответ 409 `REQUEST_NOT_OPEN`, перенос не выполняется повторно.
- **Ошибки:** `REQUEST_NOT_OPEN`, `CALENDAR_ENTRY_LOCKED`, `DATE_IN_PAST`, `OFFLINE`
- **Экран:** Запросы клиентов
- **Связи:** BR-DATE-003, BR-SYNC-001

## 6. FR-WORK — Просмотр факта тренером

### FR-WORK-001 План и факт по тренировке
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-3
- **Предусловия:** Назначение выполнено или частично выполнено; есть согласие на тренировки (BR-CONSENT-003).
- **Описание:** Экран тренировки показывает по каждому упражнению и подходу: план (повторы × вес, отдых) и факт (повторы × вес). Отклонение по весу и повторам выводится числом. Показаны время выполнения и отметки «выполнено» или «пропущено».
- **Критерии приёмки:**
  - Позитивный: Дано назначено 3 подхода по 8 повторов по 60 кг, клиент выполнил 3 × 8 × 55 кг, Когда тренер открывает тренировку, Тогда показано «план 3×8×60 / факт 3×8×55, −5 кг».
  - Негативный: Дано клиент не отметил тренировку и день ещё не закончился по TZ клиента, Когда тренер открывает её, Тогда статус «не отмечено», а не «пропуск».
- **Ошибки:** `CONSENT_REQUIRED`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Факт тренировки
- **Связи:** BR-DATE-002, BR-CONSENT-003

### FR-WORK-002 Снимок версии плана в факте
- **Актор:** Система
- **Приоритет / этап:** Must / EPIC-3
- **Предусловия:** Клиент отметил факт по назначению.
- **Описание:** Факт сохраняет снимок плана: версию и состав тренировки на момент выполнения. Тренер видит факт, сопоставленный с версией, на которой выполнялось. Если план с тех пор изменён, показывается метка «план изменён после выполнения» со ссылкой на версию. Отметка факта по устаревшей версии сохраняется со своим снимком и не возвращает `PLAN_VERSION_CONFLICT` (план клиента для факта не редактируется).
- **Критерии приёмки:**
  - Позитивный: Дано факт сохранён на версии 5, план сейчас версия 7, Когда тренер открывает факт, Тогда показан состав версии 5 и метка «план изменён после выполнения».
  - Негативный: Дано клиент отправил факт с версией 5, а сервер на версии 7, Когда запрос обработан, Тогда факт сохранён со снимком версии 5, ответ 200, состав версии 7 не подменяет факт.
- **Ошибки:** `VALIDATION_FAILED`, `SERVER_ERROR`
- **Экран:** Факт тренировки
- **Связи:** BR-SYNC-002, BR-DATE-003

### FR-WORK-003 Статусы дня
- **Актор:** Система (вычисление), Тренер (просмотр)
- **Приоритет / этап:** Must / EPIC-3
- **Предусловия:** Есть назначение на день.
- **Описание:** Статус дня: «выполнено» (все подходы отмечены), «частично» (отмечены не все, но есть хотя бы один), «пропуск» (ни одной отметки и день закончился в TZ клиента), «не отмечено» (день не закончился), «перенесено» (назначение перенесено, CAL-002). Статус вычисляется на сервере, не на клиенте.
- **Критерии приёмки:**
  - Позитивный: Дано из 4 упражнений выполнены 3, день закончился по TZ клиента, Когда тренер смотрит статус дня, Тогда статус «частично».
  - Негативный: Дано день не закончился по TZ клиента и ни одной отметки нет, Когда тренер смотрит статус, Тогда статус «не отмечено», а не «пропуск».
- **Ошибки:** `SERVER_ERROR`, `OFFLINE`
- **Экран:** Календарь клиента; Факт тренировки
- **Связи:** BR-DATE-002

### FR-WORK-004 Процент выполнения за неделю
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-3
- **Предусловия:** Есть назначения на прошедшие дни текущей недели.
- **Описание:** Процент = выполненные дни / назначенные прошедшие дни × 100, округление до целого. Перенесённые и «не отмечено» из расчёта исключаются. Блок показывается в карточке клиента.
- **Критерии приёмки:**
  - Позитивный: Дано назначено 5 прошедших дней, выполнено 4, Когда тренер открывает карточку, Тогда показано «80 % за неделю».
  - Негативный: Дано за неделю нет прошедших назначений, Когда тренер открывает карточку, Тогда показано «нет данных», а не 0 % или 100 %.
- **Ошибки:** `OFFLINE`, `SERVER_ERROR`
- **Экран:** Карточка клиента: факт за неделю
- **Связи:** BR-DATE-002, BR-GATE-001

### FR-WORK-005 Комментарий тренера к тренировке [Should] [O5]
- **Актор:** Тренер
- **Приоритет / этап:** Should / EPIC-6 [O5]
- **Предусловия:** Назначение существует; есть согласие на тренировки.
- **Описание:** Тренер пишет комментарий до 500 символов к назначению. Клиент видит комментарий в своём экране «Сегодня». Комментарий не влияет на статус дня и не меняет план.
- **Критерии приёмки:**
  - Позитивный: Дано у назначения есть факт, Когда тренер пишет «Снизь вес в третьем подходе» и сохраняет, Тогда комментарий сохранён и виден клиенту за ≤30 с.
  - Негативный: Дано текст 501 символ, Когда тренер сохраняет, Тогда ответ 422 `VALIDATION_FAILED`, комментарий не сохранён.
- **Ошибки:** `VALIDATION_FAILED`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Факт тренировки
- **Связи:** BR-SYNC-001, [O5]

### FR-WORK-006 Факт без согласия на тренировки
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-3
- **Предусловия:** Назначение существует.
- **Описание:** Назначение и план тренера видны тренеру всегда, так как он их создал. Факт (отметки, статусы дня, процент) доступен только при действующем согласии на тренировки. Без согласия показывается «Клиент не разрешил доступ к тренировкам» и статусы дней скрываются.
- **Критерии приёмки:**
  - Позитивный: Дано согласие на тренировки действует и клиент отметил факт, Когда тренер открывает тренировку, Тогда факт виден.
  - Негативный: Дано согласие на тренировки отозвано, Когда тренер открывает факт, Тогда ответ 403 `CONSENT_REQUIRED`, отметки не загружаются, назначение остаётся видимым.
- **Ошибки:** `CONSENT_REQUIRED`, `OFFLINE`
- **Экран:** Факт тренировки
- **Связи:** BR-CONSENT-003

## 7. FR-NUT — План питания

### FR-NUT-001 Создание и изменение плана питания
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-3 [O6]
- **Предусловия:** Связь клиента активна.
- **Описание:** План питания содержит: ккал в день (0–10000), Б, Ж, У в граммах (0–500 каждый), текст рекомендаций до 2000 символов и период действия (даты или «по умолчанию»). Сохранение создаёт версию плана питания по правилам BR-SYNC-002, `baseVersion` обязателен.
- **Критерии приёмки:**
  - Позитивный: Дано плана питания нет, Когда тренер сохраняет 2000 ккал, Б 150, Ж 70, У 200 и текст, Тогда план создан в версии 1 и виден клиенту после обновления экрана.
  - Негативный: Дано белки −10 г, Когда тренер сохраняет, Тогда ответ 422 `VALIDATION_FAILED` с полем «Белки», план не меняется.
- **Ошибки:** `VALIDATION_FAILED`, `PLAN_VERSION_CONFLICT`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** План питания
- **Связи:** BR-NUT-001, BR-SAFETY-001, BR-SYNC-002, [O6]

### FR-NUT-002 Предупреждение о нижнем пороге калорий
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-3
- **Предусловия:** Введено значение ккал.
- **Описание:** Если ккал меньше `NUTRITION_MIN_KCAL` (1200, провизорно), экран показывает «Ниже 1200 ккал в день. Проверьте план» и требует подтверждения «Сохранить всё равно». Сохранение не блокируется. Сервер возвращает предупреждение `NUTRITION_BELOW_MIN_KCAL` в `warnings[]`.
- **Критерии приёмки:**
  - Позитивный: Дано введено 1100 ккал, Когда тренер нажимает «Сохранить» и подтверждает «Сохранить всё равно», Тогда план сохранён, ответ содержит `warnings[]` с `NUTRITION_BELOW_MIN_KCAL`.
  - Негативный: Дано введено 1100 ккал, Когда тренер нажимает «Отмена» в предупреждении, Тогда план не отправлен, версия не меняется.
- **Ошибки:** `NUTRITION_BELOW_MIN_KCAL` (предупреждение), `OFFLINE`
- **Экран:** План питания: предупреждение
- **Связи:** BR-NUT-001, BR-SAFETY-001

### FR-NUT-003 Согласованность калорий и БЖУ [O6]
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-3 [O6]
- **Предусловия:** Введены Б, Ж, У и ккал.
- **Описание:** Экран считает ккал по формуле 4·Б + 4·У + 9·Ж и показывает расчёт рядом с введённым значением. Если расхождение больше `MACRO_TOLERANCE_PCT` (10 %), показывается предупреждение и кнопка «Подставить расчёт». Сохранение возможно после подтверждения. Сервер возвращает `MACRO_KCAL_MISMATCH` в `warnings[]`.
- **Критерии приёмки:**
  - Позитивный: Дано Б 150, Ж 70, У 200 (расчёт 2030 ккал) и введено 2000 ккал, Когда тренер меняет поля, Тогда расхождение 1,5 %, предупреждения нет.
  - Негативный: Дано Б 150, Ж 70, У 200 и введено 2600 ккал, Когда тренер смотрит поле ккал, Тогда показано «Расхождение 28 %, расчёт по БЖУ 2030 ккал» и предупреждение.
- **Ошибки:** `MACRO_KCAL_MISMATCH` (предупреждение), `OFFLINE`
- **Экран:** План питания
- **Связи:** BR-NUT-002, [O6]

### FR-NUT-004 Дневник питания клиента (только чтение) [Should] [O6]
- **Актор:** Тренер
- **Приоритет / этап:** Should / EPIC-6 [O6]
- **Предусловия:** Есть действующее согласие на питание (BR-CONSENT-003).
- **Описание:** Тренер видит за последние 14 дней приёмы пищи клиента, продукты, граммы, КБЖУ за день и сравнение с планом питания. Редактирования дневника тренером нет.
- **Критерии приёмки:**
  - Позитивный: Дано согласие на питание есть, Когда тренер открывает день, Тогда видны приёмы пищи, сумма КБЖУ за день и отклонение от плана.
  - Негативный: Дано согласие на питание не выдано, Когда тренер открывает дневник, Тогда ответ 403 `CONSENT_REQUIRED`, блок показывает «Клиент не разрешил доступ к питанию».
- **Ошибки:** `CONSENT_REQUIRED`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Дневник питания клиента
- **Связи:** BR-CONSENT-003, [O6]

### FR-NUT-005 Текст о назначении плана на экранах планов
- **Актор:** Тренер

- **Предусловия:** Открыт экран плана питания или редактор тренировок.

  - Негативный: Дано тренер открыл план питания офлайн, Когда экран загрузился, Тогда текст виден, а данные плана показаны как `OFFLINE`.

## 8. FR-PROG — Замеры клиента (только при согласии)

### FR-PROG-001 Просмотр замеров при согласии
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-3
- **Предусловия:** Действующее согласие на замеры (BR-CONSENT-003).
- **Описание:** Блок «Замеры» в карточке показывает последние 20 записей за 90 дней: дата, вес, обхваты (талия, грудь, бедро, см) и изменение к предыдущей записи. Фото не показываются в MVP.
- **Критерии приёмки:**
  - Позитивный: Дано согласие на замеры есть и клиент внёс 25 записей, Когда тренер открывает карточку, Тогда показаны 20 последних записей с изменением к предыдущей.
  - Негативный: Дано согласие есть, клиент замеров не вносил, Когда тренер открывает блок, Тогда показано «Замеров пока нет», а не ошибка.
- **Ошибки:** `OFFLINE`, `SERVER_ERROR`
- **Экран:** Карточка клиента: замеры
- **Связи:** BR-CONSENT-003, BR-DATA-003

### FR-PROG-002 Скрытие замеров без согласия
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-3
- **Предусловия:** Блок «Замеры» открыт в карточке клиента.
- **Описание:** Без действующего согласия запрос данных замеров не отправляется, блок показывает «Клиент не разрешил доступ к замерам». Если согласие есть, но запрос завершился сбоем, показывается ошибка с кнопкой «Повторить». Сообщение «нет доступа» при сбое не выводится.
- **Критерии приёмки:**
  - Позитивный: Дано согласие на замеры отсутствует, Когда тренер открывает блок, Тогда показано «Клиент не разрешил доступ к замерам», запроса данных замеров в сети нет.
  - Негативный: Дано согласие есть, сервер вернул 500, Когда тренер открывает блок, Тогда показано «Не удалось загрузить замеры» с кнопкой «Повторить», текст «нет доступа» не показан.
- **Ошибки:** `CONSENT_REQUIRED`, `SERVER_ERROR`, `OFFLINE`
- **Экран:** Карточка клиента: замеры
- **Связи:** BR-CONSENT-003

### FR-PROG-003 Замеры доступны тренеру только для чтения
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-3
- **Предусловия:** Согласие на замеры действует.
- **Описание:** Редактировать и удалять замеры может только клиент. В интерфейсе тренера кнопок «Изменить» и «Удалить» нет. На сервере запрос тренера на изменение замера отклоняется.
- **Критерии приёмки:**
  - Позитивный: Дано тренер открыл замер, Когда он смотрит на экран, Тогда кнопок «Изменить» и «Удалить» нет.
  - Негативный: Дано тренер отправил запрос на изменение замера напрямую, Когда сервер обрабатывает запрос, Тогда ответ 403 `MEASUREMENT_READ_ONLY`, данные замера не меняются.
- **Ошибки:** `MEASUREMENT_READ_ONLY`
- **Экран:** Карточка клиента: замеры
- **Связи:** BR-DATA-003

## 9. FR-NOTIF — Что получает тренер

### FR-NOTIF-201 Дайджест пропусков и неактивности
- **Актор:** Система (отправка), Тренер (получение)
- **Приоритет / этап:** Must / EPIC-4
- **Предусловия:** Включён дайджест в настройках (NOTIF-004); у тренера есть клиенты со статусом «пропуск» или «неактивен».
- **Описание:** Раз в день в 19:00 по TZ тренера приходит одно push-уведомление с числом клиентов: «Сегодня N клиентов без отметок». Нажатие открывает «Реакция сегодня». Имена, статусы по отдельности и причины в тексте не указываются (BR-DATA-003). Если подходящих клиентов нет, push не отправляется.
- **Критерии приёмки:**
  - Позитивный: Дано у тренера 3 клиента со статусом «пропуск» и TZ `Europe/Berlin`, Когда наступает 19:00 по Берлину, Тогда приходит одно push-уведомление «3 клиента без отметок», при нажатии открывается «Реакция сегодня».
  - Негативный: Дано ни у одного клиента нет статуса «пропуск» или «неактивен», Когда наступает 19:00, Тогда push не отправляется, запись в журнале «пропусков нет».
- **Ошибки:** `SERVER_ERROR` (в журнале, не на экране); отказ доставки фиксируется без персональных данных
- **Экран:** Уведомления тренера (экран блокировки); Реакция сегодня
- **Связи:** BR-DATE-002, BR-DATA-003

### FR-NOTIF-202 Push о запросе клиента
- **Актор:** Система (отправка), Тренер (получение)
- **Приоритет / этап:** Must / EPIC-4 [O3]
- **Предусловия:** Клиент создал запрос паузы (LINK-007) или переноса (CAL-007); категория «Запросы клиентов» включена.
- **Описание:** Тренер получает push в течение 60 с после создания запроса: «Новый запрос от клиента». Имя клиента, даты и причина в тексте не указываются. Счётчик в приложении обновляется при следующем получении данных.
- **Критерии приёмки:**
  - Позитивный: Дано клиент отправил запрос паузы, Когда запрос сохранён, Тогда push «Новый запрос от клиента» приходит в течение 60 с, в тексте нет имени и причины.
  - Негативный: Дано тренер выключил категорию «Запросы клиентов», Когда клиент отправляет запрос, Тогда push не отправляется, запрос виден в приложении на экране «Запросы клиентов».
- **Ошибки:** `SERVER_ERROR` (в журнале, не на экране)
- **Экран:** Запросы клиентов
- **Связи:** BR-DATA-003, BR-SYNC-001, [O3]

### FR-NOTIF-203 Уведомления без персональных данных
- **Актор:** Система
- **Приоритет / этап:** Must / EPIC-4
- **Предусловия:** Формируется любой push тренеру.
- **Описание:** Все тексты push берутся из словаря шаблонов, которые не содержат имени, фамилии, веса, замеров, питания и статусов отдельных клиентов. Подробности видны только в приложении после аутентификации. Проверка шаблонов входит в CI.
- **Критерии приёмки:**
  - Позитивный: Дано любой push тренеру, Когда он отображается на экране блокировки, Тогда текст совпадает с шаблоном из словаря и не содержит персональных данных.
  - Негативный: Дано шаблон push в словаре содержит поле с именем клиента, Когда запускается CI-проверка шаблонов, Тогда сборка падает с кодом `VALIDATION_FAILED` и указанием шаблона.
- **Ошибки:** `VALIDATION_FAILED` (в CI)
- **Экран:** Уведомления тренера (экран блокировки)
- **Связи:** BR-DATA-003

### FR-NOTIF-204 Настройки уведомлений тренера
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-4
- **Предусловия:** Онбординг завершён.
- **Описание:** Тренер включает и выключает категории: «Дайджест пропусков» (включён по умолчанию), «Запросы клиентов» (включён по умолчанию). Время дайджеста выбирается в диапазоне 17:00–21:00 (по умолчанию 19:00). Изменение действует сразу после сохранения.
- **Критерии приёмки:**
  - Позитивный: Дано дайджест включён, Когда тренер выключает его и сохраняет, Тогда в 19:00 push не приходит.
  - Негативный: Дано тренер выбрал время 23:00, Когда он сохраняет, Тогда ответ 422 `VALIDATION_FAILED` с полем «Время», настройка не меняется.
- **Ошибки:** `VALIDATION_FAILED`, `OFFLINE`, `SERVER_ERROR`
- **Экран:** Настройки уведомлений
- **Связи:** BR-DATE-002

### FR-NOTIF-205 Запасной канал без push
- **Актор:** Тренер
- **Приоритет / этап:** Must / EPIC-4
- **Предусловия:** Разрешение на push не выдано или отозвано.
- **Описание:** Бейдж «Реакция сегодня» показывает число клиентов и открытых запросов, как при открытии приложения, так и на экране списка. Баннер «Включите уведомления, чтобы не пропустить запросы» показывается не чаще одного раза в 7 дней.
- **Критерии приёмки:**
  - Позитивный: Дано разрешение на push отключено и есть 2 клиента для реакции, Когда тренер открывает приложение, Тогда бейдж показывает 2, баннер показан.
  - Негативный: Дано баннер показан вчера, Когда тренер снова открывает приложение, Тогда баннер не показан.
- **Ошибки:** `OFFLINE` (бейдж показывает последнее известное значение с отметкой «обновлено N мин назад»)
- **Экран:** Список клиентов; Настройки уведомлений
- **Связи:** BR-SYNC-001

## 10. Допущения и вопросы

Решения O1–O8 приняты по рекомендациям `00-validation.md`. Зависимые требования помечены тегом `[O#]`. Смена решения меняет правило в одном месте (раздел 0.6).

### 10.1 Допущения
1. **Модуль FR-ACCT добавлен.** Онбординг, удаление аккаунта, экспорт, адаптив и офлайн не относятся к перечисленным модулям задачи, поэтому вынесены в отдельный модуль. Владелец может переназначить их в другие модули.
2. **Статус «без плана»** (раздел 0.3) — допущение: в исходном списке статусов его нет. Без него клиент без назначений попадает в «в плане», что вводит в заблуждение.
3. **`NOT_ACTIVE_DAYS` = 7** фиксировано для MVP. Настройка тренером (3–14 дней) не включена.
4. **Диапазоны повторов** («8–10») в MVP не поддерживаются, только одно число.
5. **Предел тренировок в день** (`WORKOUTS_PER_DAY_MAX` = 3) — допущение, не из источников.
6. **Push-задержка 60 с** (NOTIF-002) и 19:00 для дайджеста — допущения, проверяются на бете.
7. **Порог ккал 1200 провизорный.** Утверждает специалист по питанию (BR-NUT-001) до бета-теста. Без утверждения NUT-002 не релизится.
8. **Квалификация — самодекларация** (BR-SAFETY-002). Верификация документов тренера в MVP не выполняется; решение владельца по плану, раздел 7.2, остаётся открытым.
9. **Код инвайта показывается один раз** (BR-INVITE-004), так как в БД хранится хэш. Повторный показ невозможен; при утере тренер отзывает инвайт и создаёт новый.
10. **Экспорт тренера** включает только данные тренера (BR-DATA-002). Данные клиентов клиент получает по собственному запросу.
11. **Удаление тренера**: клиенты видят статус «тренер удалил аккаунт», но не получают данных тренера. Срок 30 дней (BR-DATA-001) укладывается в «не позднее 1 месяца» (`00-validation`, раздел 4).
12. **Импорт CSV** (CLIENTS-005) создаёт инвайты, не связи. Лимит 5 инвайтов в час (BR-INVITE-002) несовместим с импортом 200 строк, поэтому для импорта принят отдельный лимит «один запуск в сутки» (см. вопрос 2).
13. **Собственные упражнения тренера** вне MVP, справочник наполняется заранее.
14. **Пауза, инициированная тренером** (LINK-006), не закрывает доступ к данным, как и пауза клиента (O3). Если владелец решит иначе, меняется BR-LINK-002 и тексты LINK-006/007.
15. **Комментарий тренера** (WORK-005) — Should по рекомендации O5; если скептик прав и его вырезают, требование переносится в «вне MVP».
16. **Шаблоны, перенос по запросу клиента, копирование недели и дневник питания** — Should, EPIC-6. Если они не войдут в бету, это не блокирует критерий беты (раздел 1 плана).
17. **Адаптив** — только мобильные устройства и планшеты. Веб-кабинет тренера вне MVP (план, раздел 1).

### 10.2 Открытые вопросы владельцу
1. **O5 (подтвердить):** экран «Реакция сегодня», импорт CSV и напоминания клиенту — Must для беты? Скептик предлагает вырезать импорт, решает основатель.
2. **Импорт и лимит 5/час:** принять отдельный лимит импорта «один запуск в сутки» (как сейчас) или импорт не создаёт инвайты вовсе и клиенты добавляются вручную?
3. **O8 (подтвердить):** тренеры только онлайн с 10+ клиентами — это поля в онбординге для отбора пилота или жёсткий гейт в приложении? В документе принято: поля для отбора, гейта нет.
4. **NOT_ACTIVE_DAYS:** 7 дней фиксировано или тренер настраивает (3–14)?
5. **Порог ккал 1200:** подтвердит ли специалист по питанию значение и текст предупреждения?
6. **Текст дисклеймера (NUT-005)** и текст согласий (CLIENTS-008) — проверит юрист до беты?
7. **Пауза тренером и клиентом:** подтверждаете, что пауза не закрывает доступ тренера (O3)?
8. **Запросы клиентов:** отдельный экран «Запросы клиентов» или раздел внутри «Реакция сегодня»? В документе — отдельный экран, на связи с CLIENTS-003 не влияет.
9. **Лимит тренировок в день (3)** — правильный ли порог?
10. **Удаление аккаунта тренера:** нужен ли короткий льготный период восстановления (вопрос восстановления аккаунта из `00-validation`, раздел 4)? В документе восстановления нет.
11. **Перенос тренировки клиентом (CAL-007):** окно 3 дня и 2 переноса в неделю — дефолты, которые тренер может менять, или фиксированные правила?
12. **Экспорт тренера:** достаточно ли JSON, или нужен читаемый формат (CSV/PDF) для юридического запроса?

### 10.3 Итог
Требований: 63 (ACC 9, LINK 9, CLIENTS 9, PLAN 10, CAL 7, WORK 6, NUT 5, PROG 3, NOTIF 5). Must: 55. Should: 8 (все в EPIC-6). Теги [O#] стоят на 12 требованиях.
