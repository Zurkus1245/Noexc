## 0. Короткий ответ основателю

- Сейчас приложение работает только онлайн. Локальной БД и персистентного кэша нет: данные живут в памяти TanStack Query и очищаются при выходе (`endSession`).
- Офлайн-запись в MVP запрещена `CLAUDE.md` §6: «Offline = explicit error, never fake saved». Это изменение архитектуры: нужен ADR и явное одобрение владельца. Документ правило не обходит.
- Уровни: **T0** (входит в MVP: онлайн-запись, явная ошибка офлайн), **T1** (кэш чтения, нужен ADR-0007), **T2** (очередь подходов на устройстве, нужен ADR-0008, готовый WorkoutLog из EPIC-3 и решение владельца). В MVP только T0. T1 и T2 не начинаются без ADR.

## 3. T1: кэш чтения

### 3.1 Что кэшируется

| Данные | Ключ кэша | TTL (предложено, утвердить) | Ограничение | Включение |
|---|---|---|---|---|
| План клиента: версия N и структура (read-only) | `plan:{linkId}:v{N}` | до 7 дней, с меткой возраста после 24 ч | Номер версии виден на экране (BR-SYNC-001) | T1, EPIC-2 |
| «Сегодня»: тренировка дня | `today:{linkId}:{date}` | 24 ч | Без статуса факта и отметок (C07, OF-2) | T1, EPIC-2 |
| Календарь: неделя ±1 (окно 14 дней) | `cal:{linkId}:{from}:{to}` | 24 ч | Диапазон не больше 42 дней (FR-CAL-105) | T1, EPIC-2 |
| План питания: цели КБЖУ на день | `nut:{linkId}:{date}` | 24 ч | Ст. 9: только при действующем `health_data` и после DPIA | Выкл., EPIC-3 |
| Не кэшируется: факт, отметки, итоги, пропуски, перенос, профиль, согласия, статус связи, токены | не кэшируется | - | Статусы `ended` и `paused` не показываются из кэша; токены только в `expo-secure-store` (NFR-SEC-006) | - |

Оценка размеров (предложено, измерить на эталонном устройстве): план до 200 КБ JSON, календарь на 14 дней до 100 КБ, весь кэш до 5 МБ.

### 3.2 Хранилище: TanStack Query persist + MMKV или expo-sqlite

| Критерий | Вариант A: persist + MMKV | Вариант B: expo-sqlite (таблица `cache`) |
|---|---|---|
| Код | Минимум: persister подключается к существующему `queryClient` | Свой persister: ключ, JSON, `fetched_at`, `schema_version` |
| Запись и запросы | Синхронная запись; сериализуется весь кэш при каждом сохранении, при росте до МБ заметна задержка. Запросы только по ключу | Частичные записи, транзакции, индексы, SQL по полям |
| Шифрование | `encryptionKey` в MMKV (проверить API) | SQLCipher-вариант (проверить наличие в SDK) |
| Порог выбора | До 5 МБ, один-два ключа на связь | Выше 5 МБ или при T2 |

Рекомендация: вариант A для T1 (MMKV уже в стеке CLAUDE §3, в ADR-0007 нужна только запись). Если T2 одобрена, оба уровня переводятся на SQLite, чтобы не держать два движка.

### 3.3 Версия схемы кэша

- Константа `CACHE_SCHEMA_VERSION` в `packages/contracts` пишется в каждую запись. Несовпадение версии: запись удаляется, не мигрируется. Кэш одноразовый, миграции не нужны. Миграции нужны только для outbox (раздел 4.4).
- Версия API ниже минимальной (CLAUDE §6): кэш не показывается, экран обновления (S42).

### 3.4 Правила показа

- Время в баннере берётся из заголовка `Date` ответа сервера, часам устройства не доверяем; без заголовка используется время записи.
- TTL истёк или кэш пуст: экран «Нет сети. Повторить» (S17), старые данные не показываются.

## 4. T2: офлайн-запись выполнения через outbox

### 4.1 Что пишется офлайн (только факт подходов клиента)

| Действие | Офлайн в v1 | Комментарий |
|---|---|---|
| Старт тренировки (`in_progress`, снимок версии N из кэша) | Да | Клиентский UUID; BR-DATA-001 |
| Отметка подхода «выполнено» (вес, повторы) | Да | Значения по NFR-LIMIT-005; вне диапазона ошибка до очереди |
| Подход «пропущен» с кодом причины; таймер отдыха локально | Да | «Боль»: текст о прекращении нагрузки. Таймер на сервер не уходит |
| Завершение тренировки (`completed` / `partial`) | Нет в v1 | Явная ошибка «Тренировка не завершена на сервере» (JRN-04 шаг 5) |
| Редактирование отправленного подхода | Нет в v1 | Нужна версия записи; вне MVP |

### 4.2 Что НИКОГДА не пишется офлайн (ни в T1, ни в T2 без нового ADR)

| Действие | Причина |
|---|---|
| Создание и погашение инвайта | Одноразовый код, rate-limit, единый 404 (BR-INVITE-001…009) |
| Выдача и отзыв согласий | Отзыв действует сразу (BR-CONSENT-006); офлайн-отзыв дал бы ложное «отозвано» |
| Отвязка, пауза, запрос паузы | Закрывает доступ немедленно (BR-LINK-007); состояние связи серверное |
| Назначение и правка плана тренером | Новая `PlanVersion`, конфликт `PLAN_VERSION_CONFLICT` (BR-DATA-002) |
| Перенос тренировки клиентом | Лимиты и правила (FR-CAL-107), серверная проверка |
| Ввод веса, замеров, итогов питания | Данные ст. 9; вне T2 v1, возможный T2.1 отдельным ADR |
| Импорт CSV, комментарии, экспорт, удаление аккаунта, вход, refresh, смена TZ | Серверная обработка; удаление и смена TZ подтверждаются сервером (BR-DATE-001) |

### 4.3 Запись outbox: поля и статусы

- Поля: `clientUuid` (UUID v4, создаётся вместе с записью и неизменяем), `linkId`, `workoutKey`, `planVersion`, замороженный `payload`, `idempotencyKey` (один на запись), `status`, `attempts`, `createdAt`, `lastAttemptAt`.
- Тело неизменяемо: сервер хеширует метод, путь и тело (`idempotency.interceptor.ts`). Правка означает новую запись с новым ключом.
- Статусы UI:
  - «Не отправлено»: в очереди, сеть не отвечала. Кнопка «Повторить».
  - «Отправляется»: запрос в полёте.
  - «Сохранено»: только по ответу 2xx с телом сервера. Локально не выставляется никогда.
  - «Не сохранено: причина»: 4xx (`VALIDATION_FAILED`, `WORKOUT_NOT_IN_PLAN`, `INVALID_TRANSITION`). Автоповтора нет.
- Запрос был в полёте, приложение перезапущено: показывается «Не отправлено, проверяем». Повтор идёт с тем же ключом, сервер отдаёт сохранённый ответ.

### 4.4 Порядок, повторы, лимиты, срок

- FIFO, один запрос в полёте на пользователя. Старт тренировки уходит раньше своих подходов.
- Сеть, 5xx, таймаут: экспоненциальная задержка с jitter; при 429 учитывается `Retry-After`. После 10 автоповторов запись ждёт кнопки «Повторить» (предложено).
- Лимит очереди: 300 записей (предложено). При переполнении добавление блокируется с сообщением, молчаливого удаления нет.
- Срок: 72 ч (предложено). Ключ идемпотентности живёт 24 ч (BR-SYNC-003), поэтому защита от дубля дольше суток обязана быть серверной: уникальность `(linkId, clientUuid)` в таблице подходов. Без неё TTL больше 24 ч запрещён.
- Истёкшая запись: «Не сохранено: срок истёк», действия «Скопировать» и «Удалить». Не удаляется молча.
- Миграции outbox: `PRAGMA user_version`, только вперёд, тест на каждую версию. Неизвестная версия: синхронизация блокируется, данные не стираются.
- Смена аккаунта (JRN-13 шаг 5): очередь прежнего аккаунта не отправляется; до входа показывается предупреждение о стирании.

## 6. Шифрование и удаление данных на устройстве

### 6.1 Шифрование

- Ключ 256 бит создаётся при первом запуске T1 и хранится в `expo-secure-store` отдельно от токена; он задаёт `encryptionKey` MMKV или ключ SQLCipher. Удаление ключа = криптостирание: данные становятся нечитаемыми.
- Ограничения: iOS Keychain переживает удаление приложения (маркер установки при первом запуске стирает старый кэш); класс доступности ключа выбрать в ADR-0007 (Q4); root и jailbreak шифрование не защищают; файлы БД исключаются из облачных копий (iCloud, Google Auto Backup), проверить настройки Expo.

### 6.2 Матрица очистки

| Событие | Что стирается на устройстве | Когда |
|---|---|---|
| Выход (`endSession`) или смена аккаунта | Весь кэш. Очередь T2 сохраняется для этого аккаунта; при выходе предупреждение (JRN-13 шаг 4). При смене аккаунта очередь стирается после подтверждения | Сразу |
| Собственная отвязка (`ended`) | Кэш и календарь этой связи | Сразу после ответа сервера |
| Серверное завершение (тренер, админ, удаление тренера) | Кэш связи | При первом контакте: 403, 404 или статус `ended` |
| Отзыв согласия `health_data` или `coach_access` | Health-кэш (питание, план) и кэш связи | При ответе сервера; офлайн-отзыва нет |
| Удаление аккаунта | Всё, включая ключ | После подтверждения сервером |
| Переустановка приложения | Всё по маркеру установки | При первом запуске |
| Истёк TTL | Запись | При чтении и при старте |

Текущий `endSession` вызывает `queryClient.clear()` только в памяти. С persist он должен стирать и хранилище кэша (BL-OFF-08).

## 7. Связь отозвана, пока устройство офлайн

- Окно риска: от серверного события (отвязка, блокировка админом, отзыв с другого устройства) до ближайшего контакта с сервером. Кэш может показать план или календарь после отвязки. Сервер до устройства не дотягивается.
- Меры: TTL 24 ч для календаря и питания, до 7 дней для плана (предложено); баннер «Данные могут быть неактуальны» с временем; purge при первом онлайн-контакте; статусы `ended` и `paused` не кэшируются как текущие; с устройства никакие данные связи не запрашиваются и тренеру ничего не уходит.
- Остаточный риск: TTL офлайн плюс украденное включённое устройство. Владелец принимает риск или ставит TTL 0 для health-данных (T1 без питания).
- GDPR: кэш health-данных на устройстве относится к обработке по согласию (ст. 9); минимизация (только для экрана), ограничение хранения (TTL, purge по матрице), удаление при следующем контакте, не позже месяца (NFR-PRIV-007). Добавить строку «Кэш на устройстве» в реестр ст. 9 (`03-nfr.md`, раздел 9) и обновить DPIA до включения T1 (NFR-PRIV-012).

## 10. Тесты и метрики

Тесты:
- **Maestro, режим самолёта** (эталонное устройство, iOS и Android):
  - T0: вход без сети показывает «Нет соединения», подход не помечается «Сохранено»; после включения сети действие повторяется.
  - T1: прогрев кэша онлайн, сеть выключена: «Сегодня» с баннером; перезапуск офлайн; истёкший TTL даёт «Нет сети. Повторить»; выход очищает кэш.
  - T2: сценарий 8.1 целиком; убить приложение в статусе «Отправляется»; после запуска «Не отправлено, проверяем», сеть, на сервере ровно одна запись.
- **Контрактные и интеграционные (Testcontainers):** повтор с тем же ключом возвращает тот же ответ; другое тело даёт `IDEMPOTENCY_CONFLICT`; повтор подхода с тем же `clientUuid` после 24 ч не создаёт дубль; лишние поля отбрасываются (CLAUDE §6).
- **Unit и миграции:** переходы статусов outbox; запрет «Сохранено» без 2xx; backoff; лимит; TTL; версия кэша; тест на каждой версии схемы SQLite.
- **Безопасность:** статический поиск токенов в MMKV и SQLite (NFR-SEC-006); purge при `endSession`; после удаления ключа данные нечитаемы.

Метрики (без PII, только агрегаты и bucket, NFR-PRIV-005):

| Метрика | Определение | Цель (предложено) | Источник |
|---|---|---|---|
| Доля очереди | Подходы в «Не отправлено» и «Отправляется» / все подходы за сутки | Тревога при росте выше 5% у пользователя за сутки | `offline_queue_depth_bucket` |
| Возраст самой старой записи (p95) | Минуты от `createdAt` | Не больше 60 мин после восстановления сети | Клиентский bucket |
| Время до отправки после восстановления сети (p95) | От появления сети до последнего ответа очереди | Не больше 1 мин (JRN-13) | `queue_flushed {count_bucket}` |
| Ложное «Сохранено» и молчаливые потери | Случаи без 2xx; удаления без подтверждения | 0 (блокер релиза) | Тест и лог-инвариант |
| Серверные дубли подходов | Записи с одинаковым `(linkId, clientUuid)` | 0 | Запрос к БД |
